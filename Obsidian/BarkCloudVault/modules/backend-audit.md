## Реализации и проверки их авторов — история

Следующие записи описывают результаты реализации отдельных задач. Актуальный вывод повторного аудита и остатки F19/F20 находятся выше.

**Статус F01 — исправлено (2026-10-02):** грант на файл больше не действует, пока файл в корзине у выдавшего его владельца. `GrantStorage.RecipientHasAccess` (отсюда `GetSharedFileDownloadUrl`), `ListSharedWithMePage` («мне доступны») и секция Shared единого поиска (`LoadShared`, включая `ResolveHit`) фильтруют гранты общим предикатом `FileGrantQueries.WhereOwnerFileNotTrashed`: грант активен, если у `grant.OwnerId` есть живая запись файла или нет ни одной записи в корзине (семантика `GetEffectivelyTrashedFileIds`; файлы без `CloudFileEntry` остаются доступными — строгая проверка «нужна живая запись» сломала бы шаринг галерейных файлов без привязки к папке). Сам `FileGrant` при переносе в корзину сохраняется: после `RestoreFromTrash` доступ возвращается, окончательная зачистка по-прежнему удаляет гранты. Фильтр выполняется в SQL до `LIMIT`, страницы «мне доступны» остаются полными. Исходящие гранты владельца (`ListMyOutgoingShares*`, `Remove`) не менялись, миграции и proto тоже. Проверено: 10 SQLite-тестов `GrantStorageTests` (корзина, restore, файл без записей, одна запись в корзине и одна живая, соучастник-владелец, чужой получатель, полная страница, исходящие гранты) и три существующих PostgreSQL-теста поиска `UnifiedSearchPostgresTests` (Search Shared, ResolveHit, скрытые названия) с файлом в корзине дарителя — без фильтра в поиске они падают; весь набор Files — 489 тестов на PostgreSQL 17 прошёл. Остаётся: уже выданные временные ссылки (`TempFile`) действуют до конца `TempFiles:ExpiresAt`; нагрузочно проверка «нет записей в корзине» для файлов без записей не измерялась (отдельный индекс не добавлялся). Подробности — [[modules/backend-files]] · [[api/files-api]].

**Статус F12 — исправлено (2026-10-02):** `LegacyUploadAdmissionFilter` ставит per-request `MinDataRate` только на HTTP/1.x; на HTTP/2/3 Kestrel не поддерживает его (сеттер бросает `NotSupportedException` → 500 после выдачи слота), поэтому присваивание пропускается, остальные ограничения (допуск, потолок тела, бюджет) действуют. Проверено на настоящем Kestrel с h2c-слушателем (`LegacyUploadKestrelTests.ValidUpload_OverHttp2_…`) и unit-тестом фильтра. Остаточный риск: на HTTP/2 нет защиты от медленного клиента (глобальный `MinRequestBodyDataRate = null`); HTTP/2 достижим только через прямой gRPC-порт, nginx и Torrent ходят по HTTP/1. См. [[modules/upload-2]].

**Статус F19 — исправлено (2026-10-02):** письма Identity больше не влияют на результат основной операции. После коммита хендлеры вызывают `INotificationOutbox.EnqueueAsync` (вставка в таблицу `PendingNotifications`, не бросает); адрес из Users, геолокацию и публикацию в RabbitMQ выполняет `NotificationOutboxWorker` с повторами (пауза 30 с · 2^(n−1) до 1 ч, срок жизни 24 ч, захват строк через lease для нескольких реплик). Через outbox идут `FailedLogin`, `SuccessfulLogin`, `SuccessfulRegistration`, `PasswordChanged`, `PasswordChangedByAdmin`, `TwoFactorMethodChanged` — в `Auth`, `SessionIssuer`, `SetPassword`/`ConfirmResetPassword`, `ConfirmAccount`, `DisableOtp`/`ConfirmOtp`, `ForceSetPasswordServer`. Вход паролем, по ключу и `CreateSessionForUserServer` выпускают сессию единым `SessionIssuer`. `LocationClient` ждёт геолокацию не дольше 2 с. Письма с кодами (`CreateAccount`, `ResetPassword`, email-код входа и привязки) остаются синхронными. Остаётся: доставка как минимум однократная; письмо теряется, если процесс упадёт между основным коммитом и вставкой строки; если отправка email-кода упала после его выдачи, повторный запрос в пределах cooldown письмо не отправит (отдельный вопрос, не F19). Проверено: 309 юнит-тестов Identity и 22 PostgreSQL-теста (два воркера не дублируют письма, письмо доставляется после восстановления Users, миграция `Down → Up`); EF-модель согласована с миграциями, solution собирается. Подробности — [[modules/notification-outbox]] · [[modules/backend-identity]].

**Статус F20 — исправлено (2026-10-02):** `UnifiedSearchService` больше не материализует каталог: каждая запрошенная секция — один запрос к БД с рангом (`exact/prefix/substring/typo`), keyset-условием по курсору и `LIMIT limit+1`; связанные данные (метаданные, алиасы, теги, избранное, превью) грузятся один раз и только для файлов страницы; `ResolveHit` — точечный запрос по id с той же проверкой доступа. Формат курсора, proto и схема БД не менялись. Проверено: 28 PostgreSQL-тестов `UnifiedSearchPostgresTests` (паритет ранжирования, обход курсором для всех секций, видимость, число прочитанных строк и SQL-команд — два теста объёма чтения до исправления падали: 4014 и 4016 строк) и 6 SQLite-тестов; весь набор Files — 477 тестов на PostgreSQL 17 прошёл. Замер на 100 тыс. фото: широкий поиск 247 → 0,4 МБ и 203 314 → 27 строк, `ResolveHit` 362 → 1,4 мс. Остаётся: условие `word_similarity` не использует trigram-индекс, поэтому БД считает ранг по всем совпадениям — время растёт с их числом, но память и передача данных — нет; сходство опечаточного тира теперь `pg word_similarity` (ранги 2–4 прежние); нагрузочный p95 при многопользовательской нагрузке не снимался. Подробности — [[modules/backend-files]].

**Статус F13 — исправлено (2026-10-02):** замок дерева (`ICloudHierarchyStorage.LockTree`) теперь берут все писатели, которые ссылаются на папку: `CreateDirectory`, `AttachFile` (включая выбор системной папки при `route_by_media_kind`), `MoveFileEntry`, `RestoreFromTrash`, `CreateFolderShare`, `ShareFolderWithUser`; порядок — замок → проверка → запись → commit, запись активности — после commit. `RestoreFromTrash`, `CreateFolderShare` и `ShareFolderWithUser` аудитом не названы, но имели ту же гонку с `DeleteDirectory`. Проверено: 7 новых PostgreSQL-тестов `CloudTreeWriterRacePostgresTests` (писатель останавливается после проверки папки и до записи, затем стартует `DeleteDirectory`) до правки падали все 7 — подпапка, живая запись, публичная ссылка и грант на удалённую папку, после неё проходят; юнит-тесты порядка «замок → проверка → запись → commit» для всех шести хендлеров; весь набор Files — 513 из 513 на PostgreSQL 17 (без PostgreSQL 448 + 65 пропущено). В `CloudDirectoryUniquenessPostgresTests` хелпер `Create` пишет через `AddDirectory` мимо хендлера, потому что хендлер теперь сериализует создания одного владельца, а там проверяются сами уникальные индексы. Остаётся: FK на `ParentId`/`DirectoryId` нет (корень `Guid.Empty` и записи корзины мешают), существующие сироты не чинятся — диагностические SQL в [[modules/backend-files-cloud]]; `RenameDirectory` против `DeleteDirectory` может дать `DbUpdateConcurrencyException` вместо `DirectoryNotFound`. Замок сериализует структурные операции одного владельца на время нескольких запросов.
