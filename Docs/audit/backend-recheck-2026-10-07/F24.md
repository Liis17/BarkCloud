# F24 · P2 — CI пропускает зависимости и тесты Torrent

Проверено 2026-10-07 на `d6563a2160ca8e3b870c32871883aa6fa188b923`. Статус: **актуален**. Этот файл можно целиком передать агенту как задание.

## Проблема и причина

Все семь сервисов напрямую ссылаются на `BarkCloud.GrpcServer` через `ProjectReference`. Но [backend-service-ci.yml:75](/Users/liis/Projects/BarkCloud/.github/workflows/backend-service-ci.yml:75) считает runtime-изменениями только свою папку, `Shared/**` и rebuild trigger. Внешние `push.paths` файлов `build-backend-*.yml` тоже не включают GrpcServer и общие build-файлы. В [tests.yml:43](/Users/liis/Projects/BarkCloud/.github/workflows/tests.yml:43) изменение GrpcServer запускает его тесты, но не проверки потребителей. Правка общей аутентификации/интерцепторов может остаться без тестов потребителей и без выпуска обновлённых образов.

Изменения `Directory.Build.props` и `Tests/Directory.Build.props` не учтены, хотя первый импортируется всеми проектами, а второй задаёт параметры тестовых проектов и импортирует первый.

Тестовый проект Torrent есть, но отсутствует в автоматическом [tests.yml](/Users/liis/Projects/BarkCloud/.github/workflows/tests.yml:25), ручной [матрице:37](/Users/liis/Projects/BarkCloud/.github/workflows/tests-backend-manual.yml:37) и параметрах [build-backend-torrent.yml:29](/Users/liis/Projects/BarkCloud/.github/workflows/build-backend-torrent.yml:29). В последнем нет `test-path`/`test-project-path`, поэтому `has_tests=false`: образ Torrent выпускается без этих тестов.

Отдельный пробел в [условии build:194](/Users/liis/Projects/BarkCloud/.github/workflows/backend-service-ci.yml:194): `needs.test.result != 'failure'` допускает результат `skipped`. Например, отказ обязательного `check_dotnet` пропускает test-job, но этот фильтр публикации его не блокирует. Поэтому подключения Torrent.Tests недостаточно для гарантии «публикация только после успешных обязательных тестов».

## Что исправить

1. Согласовать **три уровня**: внешние события `push.paths`, runtime/test фильтры reusable workflow, PR-фильтры и условия jobs в `tests.yml`.
2. Изменение GrpcServer должно проверять/пересобирать всех его фактических backend-потребителей: Configuration, Files, Identity, Notification, Torrent, Users, Web. Изменение общих build-настроек должно запускать соответствующие проверки; правка только тестовых настроек не обязана публиковать образы.
3. Добавить Torrent.Tests в PR/workflow_dispatch, ручную матрицу и CI/CD Torrent, включая triggers на его тесты/TestKit и параметры reusable workflow.
4. Учесть Identity/Users integration jobs при изменении общих runtime-зависимостей. Сохранить существующие PostgreSQL/RabbitMQ зависимости этих jobs и текущие правила proto; массово менять политику proto в этой задаче не нужно.
5. Исправить условие публикации reusable workflow: если `should_test=true`, требуется именно `needs.test.result == 'success'`. Разрешить пропуск только когда тестирование по правилам действительно не требуется. Не приравнивать `skipped` обязательного test-job к успешной проверке.

## Приёмка

Проверить таблицу изменённых путей и ожидаемых jobs, затем валидность YAML/Actions:

- Только `Backend/BarkCloud.GrpcServer/XAuth/XAuthExtensions.cs`: все семь потребителей проверяются; их deploy-workflows запускаются.
- Только корневой `Directory.Build.props`: нужные backend/shared проверки и пересборки не пропускаются.
- Только `Tests/Directory.Build.props`: тесты запускаются, публикации без runtime-изменений не добавляются.
- Только тест Torrent: запускается Torrent.Tests, production-сборка без необходимости не стартует.
- Только production Torrent: его тесты обязательны перед публикацией.
- Ручной backend-прогон включает Torrent. Ошибка его теста блокирует публикацию.
- Отказ prerequisite (`check_dotnet`) и пропуск обязательного test-job блокируют публикацию; отсутствие обязательных тестов по правилам рассматривается отдельно.
