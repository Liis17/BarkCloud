## Проблема и причина

[SearchRanking.cs:31](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Files/Services/SearchRanking.cs:31) фильтрует и ранжирует через PostgreSQL `word_similarity(value, query)` с порогом `0.45`. После SQL-выборки [CreateHit:313](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Files/Services/UnifiedSearchService.cs:313) заново выбирает совпавшее поле через C# [Match:341](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Files/Services/UnifiedSearchService.cs:341). Это другой алгоритм: [WordSimilarity:367](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Files/Services/UnifiedSearchService.cs:367) берёт максимальный Dice-score триграмм для каждого слова значения и полного значения.

Одинаковые имена методов не означают одинаковые метрики. PostgreSQL ищет непрерывный участок триграмм второго аргумента, похожий на первый; C# сравнивает множества триграмм полного запроса и значения/его слова. Поэтому SQL включит строку, которую C# отвергнет. Карточка получит пустые `MatchField/MatchValue`, либо поле с другим качеством совпадения.

Для значения `report` и запроса `quarterly report finances`: SQL-score `1`, C#-score `0.36363636363636365`, что ниже `0.45`. В SQL порядок/курсор определены одним набором правил, подпись карточки — другим. У системных умных папок ранг считается в памяти, поэтому согласование должно охватить и этот источник.

Следствие — непонятные результаты и ненадёжная подпись/подсветка совпадения. **Нарушение доступа этим воспроизведением не установлено.** Не трактуй находку как permission bypass.

## Доказательство

Динамика: PostgreSQL 18.6, актуальные миграции, настоящий `UnifiedSearchService.Search`, одна папка владельца `report`, запрос только секции Folders:

```text
query=quarterly report finances
Title=report
MatchField=""
MatchValue=""
SQL word_similarity=1
настоящий C# WordSimilarity=0.36363636363636365
```

`F20_SearchEveryReturnedFolderMustHaveMatchingField` **падает**: ожидается `MatchField=name`, фактически пустая строка. C#-score вычислен вызовом настоящего закрытого метода через reflection, а не его переписанной копией. Включение папки подтверждено полным Search, не отдельным SQL-предикатом.

От `575318a` до `d6563a2` `UnifiedSearchService` изменён ради placeholders/BuildHit; `Match`, метрики и `SearchRanking` не изменены. Статически также различается нормализация сырых полей: SQL `lower` против C# `SearchText.Normalize` с NFKC; отдельные Unicode-кейсы в этом аудите не воспроизводились.

## Задание агенту

Исправь F20 в текущей ветке: фильтрация, ранг/сходство, курсор и выбор `MatchField/MatchValue` должны описывать одно совпадение. Начни с PostgreSQL-регрессии указанного входа и тестов выбора лучшего поля.

Минимальный объём:

1. Сохрани нынешнюю SQL-выборку страниц и явно закрепи авторитетную семантику поиска. Минимально — оставить действующий PostgreSQL-score и передавать соответствующее выигравшее поле/значение вместе с SQL-результатом вместо повторного решения другим C#-алгоритмом. Возможен другой способ, если доказан паритет; не меняй молча смысл многословного поиска.
2. Согласуй порядок аргументов `word_similarity`, порог, нормализацию и выбор победителя при совпадении нескольких полей. Охвати имя, алиас, теги, metadata, description и системные умные папки; выигравшее поле должно соответствовать рангу SQL.
3. Сохрани стабильную пагинацию и действующие проверки видимости/доступа. Не возвращайся к загрузке всего каталога и не отфильтровывай строки в C# уже после `LIMIT`: это даст неполные страницы и нарушит курсор.
4. Для `ResolveHit` без поискового запроса пустые MatchField/MatchValue допустимы; не вводи ошибку для этого отдельного сценария.
5. Обнови `Obsidian/BarkCloudVault/modules/backend-files.md` и API-заметки по выбранной семантике. Не переключай ветку, не добавляй новый поисковый продукт/индексы без необходимости.

Ловушки: подставить `name` при отсутствии C#-совпадения недостаточно — реальное совпадение может быть в теге или metadata. Простая смена направления `word_similarity` изменит состав результатов, но не сделает Dice той же метрикой. SQL-фильтр и подпись карточки должны использовать одинаковую нормализацию и правило выбора поля.

## Приёмка

- Указанный многословный вход либо сохраняет текущий найденный `report` с `MatchField=name/MatchValue=report`, либо меняет выдачу только в рамках явно описанной и протестированной семантики. Результат с пустой подписью при непустом запросе недопустим.
- Проверены exact/prefix/substring/typo и значения по обе стороны порога; несколько слов, регистр, Unicode-нормализация, `%`, `_`, `\`, пунктуация, короткие запросы.
- Для каждого источника совпавшее поле соответствует тому, что определило ранжирование. Проверены совпадения по нескольким полям и детерминированные ничьи.
- Обход курсором с малым лимитом равен выдаче одной страницы: нет повторов/пропусков, не появляются пустые страницы из-за C#-фильтрации.
- Сохранены лимит чтения `limit+1`, точечный ResolveHit и отсутствие чужих данных; штатные PostgreSQL/SQLite-тесты поиска и полный Files проходят; документация обновлена.
