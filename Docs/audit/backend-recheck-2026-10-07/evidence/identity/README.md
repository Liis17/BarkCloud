# Диагностические проверки Identity

Исторический проверенный срез: `d6563a2`, дата: 2026-10-07. Это отдельный console harness, а не новый штатный тест. `results.txt` сохраняет фактический вывод того старого среза; текущий `Program.cs` адаптирован к F19-A atomicity-контракту и проверяет исправленное поведение. Он по-прежнему воспроизводит независимые диагностические наблюдения F19-B и F23.

`results.txt` — фактический вывод выполненного исторического прогона и не является oracle для текущего кода. `Program.cs` проверяет F23 через настоящий `JwtService`, F19-B через настоящий `SessionIssuer` с контролируемым незавершённым gRPC mock и F19-A через настоящий `SetPasswordCommandHandler` на PostgreSQL с trigger отказа INSERT уведомления. Для F19-A ожидается распространённая ошибка вставки при сохранённом старом пароле и пустом outbox; повторный `SaveChanges` на том же контексте не должен применить откатившийся пароль. Внешние геолокация, Users, RabbitMQ и SMTP не вызываются.

## Повторный запуск

Нужны .NET 10, доступные пакеты NuGet и **отдельный тестовый PostgreSQL**. Локальный кластер первоначального аудита остановлен; исходник не содержит его адреса, порта или credentials.

1. Подготовить отдельный PostgreSQL. Тестовому пользователю нужны подключение к `postgres`, `CREATE DATABASE` и права применения миграций в создаваемой БД.
2. Задать `BARKCLOUD_TEST_POSTGRES` строкой подключения к этому тестовому серверу. Не использовать production-сервер. Строка берётся из environment и не выводится harness.
3. Из корня repository выполнить:

```bash
dotnet run --project Docs/audit/backend-recheck-2026-10-07/evidence/identity/IdentityRecheck.csproj -c Release
```

Если harness перенесён отдельно, передать путь к checkout через `-p:BarkCloudRoot=/absolute/path/to/BarkCloud`. Внутри repository корень вычисляется автоматически.

`PostgresIdentityDatabase` создаёт БД с именем `barkcloud_identity_recheck_<GUID>`, применяет миграции Identity и удаляет **только эту созданную БД** в `DisposeAsync` через `DROP DATABASE ... WITH (FORCE)`. При аварийном завершении возможен остаток именно с этим префиксом; удалять его вручную только после проверки принадлежности прогону. Используются реальные таблицы/хранилища, не production-БД.

При фактически выполненном аудите использовался исходный штатный helper, создающий временные `barkcloud_identity_f11_<GUID>`. В переносимом артефакте префикс временной БД — `barkcloud_identity_recheck_<GUID>`.

Текущий `Program.cs` собран и запущен на отдельном временном PostgreSQL-кластере; проверка F19-A прошла, F19-B и F23 дали описанные диагностические наблюдения. Исторический `results.txt` оставлен без изменений, поэтому он не отражает текущую проверку F19-A.

## Интерпретация

Ожидаемые наблюдения текущего harness:

- F23: harness продолжает фиксировать исходы helper и signer для 15/16/31/32 байт.
- F19-B: RPC без deadline и отмены; отменённый caller остаётся ожидающим до ручного release. Эта работа не закрывает F19-B.
- F19-A: отказ INSERT передаётся владельцу, старый пароль остаётся, очередь пуста, enqueue failure учитывается.

Harness завершается успешно, когда независимые диагностические исходы F23/F19-B и исправленный критерий атомарности F19-A совпадают с ожиданиями. Это отдельная проверка, не замена штатной тестовой матрицы. Искусственные значения JWT/пароля внутри исходника — только входы диагностики.

F02 проверен существующим regression в `Identity.IntegrationTests`, а не этим harness. Полный сетевой прогон развёрнутого backend здесь отсутствует.
