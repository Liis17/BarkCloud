# Windows Drive — виртуальный диск BarkCloud

Parent: [[Architecture]] · Files API: [[Backend/Files]] · Identity: [[Backend/Identity]] · IPC и proto: [[Shared/Proto]]

## Назначение

Клиент Windows монтирует облачные каталоги как диск с буквой через Dokany. Решение состоит из WPF-приложения `BarkCloud.Drive.App`, скрытого процесса `BarkCloud.Drive.Engine` и общих IPC-контрактов `BarkCloud.Drive.Contracts`.

## Публичные контракты

- UI и Engine общаются через StreamJsonRpc на named pipe `BarkCloud.Drive.Engine.<SID>`; `EnginePipe` в Contracts получает SID через `WindowsIdentity.GetCurrent().User` и задаёт для клиента и сервера `PipeOptions.Asynchronous | PipeOptions.CurrentUserOnly`.
- При `ShutdownAsync` App освобождает RPC-прокси после ответа, закрывая pipe. После отмены lifetime Engine ждёт `JsonRpc.Completion` до 3 секунд, затем освобождает RPC и pipe.
- `IDriveEngine` предоставляет login/logout, обычный вход с OTP, вход WebAuthn, mount/remount/unmount, статус (`PendingUploads`, `LastSyncError`), аватар, настройки кеша, язык и shutdown.
- Движок использует отдельные gRPC-каналы Identity, Files/Cloud и Users; байты передаются по HTTP через Files web endpoint. Файлы отправляются legacy multipart-потоком; серверные операции описаны в [[Backend/Files]].
- Адрес сервера задаётся в `server.json` в профиле пользователя. Значения по умолчанию в `Drive/BarkCloud.Drive.Engine/appsettings.json`: `cloud.barkfluff.com`, Identity `:7020`, Users `:7021`, Files `:7025`.
- `EngineServerKey.FromConfig` нормализует HTTPS-адрес Identity и добавляет порты Files/Users. `TokenStore` хранит DPAPI-блоб `{ ServerKey, Token }`; при несовпадении ключа удаляет токен. Старый DPAPI-формат с одним токеном при первом чтении привязывается к текущей конфигурации без повторного входа.
- После входа или восстановления `UserProfile` загружает владельца через `UsersApi.GetUser(0).User.Id` и сохраняет последний известный ID в `EngineSettingsStore` по ключу сервера. Новый интерактивный вход и logout очищают этот ID до загрузки профиля; поэтому офлайн-файл при недоступном профиле получает `OwnerUserId=null`, остаётся скрытым и ждёт усыновления. При восстановлении сохранённой сессии fallback на прежний ID допустим, поскольку это тот же пользователь.
- В настройках можно менять букву диска, метку тома и папку кеша. Смена буквы/метки перемонтирует том; смена папки влияет на новые загрузки и не переносит ранее скачанные файлы.
- WebAuthn-кнопка доступна в мастере при поддержке Windows WebAuthn и доменном имени сервера. Assertion получают через Windows WebAuthn API; регистрация и управление ключами остаются вне этого клиента.

## Зависимости и взаимодействия

- `BarkCloud.Drive.App` — WPF-UI с треем и мастером первого запуска; `Engine` — `WinExe` без окна, который обслуживает Dokany и named pipe. Каждый процесс ограничен одним экземпляром на пользователя.
- `TokenManager` выполняет login и проактивно обновляет access-token через Identity. Access-token хранится в памяти; refresh-token шифруется DPAPI в `%LOCALAPPDATA%/BarkCloud.Drive/refresh.bin`. Стабильный device ID хранится рядом. Поколение защищает сессию от поздних ответов старых Auth/CreateToken/WebAuthn-запросов; новый вход и logout отменяют прежний refresh-цикл. `SessionRestored` вызывается один раз после прямого восстановления либо успешного фонового retry. Транзиентная ошибка восстановления сохраняет refresh-токен и повторяется с бэкоффом от 5 секунд до 5 минут. `OperationCanceledException` и `RpcException(Cancelled)` завершают restore/refresh штатно только при отмене собственного токена; отмена транспорта без такой отмены повторяется с бэкоффом.
- `MetadataInterceptor` добавляет device/app headers в Base64(UTF-8), а `x-auth-token` передаёт как сырой токен. Эти метаданные нужны серверной авторизации.
- Для unary gRPC-вызовов `MetadataInterceptor` задаёт deadline 30 секунд только при его отсутствии; явный deadline сохраняется. Streaming-вызовы этим правилом не затрагиваются.
- Передача файлов через HTTP использует `SocketsHttpHandler.ConnectTimeout=15 с` и `HttpClient.Timeout=Infinite`. Загрузка и скачивание отменяются после 60 секунд без прогресса; после отправки multipart-тела загрузка ждёт ответ сервера до 10 минут, чтобы не начинать большой upload заново. Каждый Range-блок дополнительно ограничен 60 секундами общего времени. Таймаут передачи выдаёт локализованный `TimeoutException`, который отображается как сетевая ошибка; outbox считает его обычной неудачной попыткой, а Attach/Move — неопределённым результатом. `BarkCloudConnection` владеет и освобождает `HttpClient`; `CloudGateway` освобождает свой таймер удалений.
- `Program.cs` захватывает операцию восстановления до создания IPC pipe; сетевой запрос продолжается асинхронно, поэтому UI может подключиться сразу, а ранний интерактивный вход не отменяется поздним стартом восстановления. После успешного восстановления `SessionRestored` загружает профиль, запускает outbox и монтирует последнюю сохранённую букву. UI и Engine могут запускаться независимо через отдельные записи автозагрузки Windows.
- Список каталогов собирается cursor-пагинацией с кешем на 5 секунд и индексами имён подпапок/файлов (`OrdinalIgnoreCase`, первое совпадение в порядке листинга). Одновременные промахи одной папки объединяются по ключу `(DirectoryId, поколение, эпоха аккаунта)`; инвалидация и смена аккаунта не позволяют старому ответу заменить новый кеш. Ожидающие повторяют загрузку при отмене владельца. `Resolve` использует индекс, отдельно учитывает тумбстоны и ищет сначала папку, затем файл только по `OrdinalIgnoreCase` (первое совпадение в порядке листинга), без приоритета точного регистра. `MoveFile` получает отфильтрованный `ListDirectory`; при тумбстонах в папке линейно ищутся источник и цель. `ResolveMoveTarget` ищет сначала папку, затем файл; `ResolveMoveSource` выбирает по `entryId` или флагу `isDirectory`. Поиск по имени в `MoveFile` сначала выбирает точное `Ordinal`-совпадение, затем fallback без учёта регистра. Ошибка или отмена загрузки не кешируется. Файлы разрешаются по пути каталога; данные читаются из облака через HTTP.
- Хэндл чтения файла хранит `ResolvedNode` в `HandleContext.Node`; хэндлы папок `HandleContext` не получают, и `GetFileInformation` папки разрешает путь. `ReadFile` использует зарегистрированную локальную копию с тем же `EntryId`, если она гидрирована, у неё есть открытый writer (`OpenCount > 0`) или это `Pending` (включая восстановленный из outbox файл). Гидрированная копия проверяется и читается под `DataSync` без ожидания `Sync`; негидрированная копия гидрируется под `LocalFile.Sync`, пока остаётся зарегистрированной. Если закрытая негидрированная копия снята с обслуживания, чтение продолжает использовать сохранённый `ResolvedNode`. `GetFileInformation` использует локальную копию, пока она находится в реестре под тем же `EntryId`. После `Persist` локальный файл получает новый `EntryId`, а старая запись уходит в корзину; открытый ранее хэндл чтения перестаёт находить локальную копию по старому ID и продолжает читать сохранённый `ResolvedNode` — снимок версии на момент открытия.
- `CreateFile` на запись существующего облачного файла регистрирует `LocalFile` с `Hydrated=false`, не скачивая содержимое. До гидрации `GetFileInformation` и `FindFiles` берут размер из `ExistingNode`. `ReadFile` через writer-хэндл гидрирует общую копию; reader-хэндл читает уже гидрированную копию под `DataSync`, не ожидая `Sync` во время upload. Если reader обнаружил негидрированную копию, гидрация выполняется под `LocalFile.Sync` с `DokanKeepAlive`. Сбой оставляет файл негидрированным, поэтому запрос можно повторить.

## Сессия, выход и кеш аккаунта

- Интерактивный вход через `LoginAsync` или `CompleteWebAuthnAsync` сериализован с logout и mount/remount/unmount одним `_sessionOperations`. Он блокирует запуск outbox, останавливает worker и при действующей сессии ограниченно отправляет буферизованные удаления под старым токеном. Смонтированный диск размонтируется до запроса новых токенов, даже если сервер уже отклонил сессию: полный цикл `Cleanup → CloseFile` сохраняет изменения старым токеном либо передаёт их в outbox со старым владельцем из профиля или LastUserId. После `Cleanup` очередь удалений ещё раз ограниченно отправляется с прежней сессией; если её нет, удаления сбрасываются из очереди, записи возвращаются в листинг, а ошибка попадает в `LastSyncError` и лог. После успешного входа очищаются кеши и профиль, загружается новый `UserId`; при неизвестном прежнем ID или смене пользователя общий `RemovePlaceholdersForAccountChange` удаляет пустые заготовки на размонтированном диске. При входе тем же пользователем заготовки сохраняются. Редкие остатки с `Modified`, `KeepData` или непустым temp-файлом скрываются из реестра, сохраняются по указанному в `LastSyncError` пути и записываются в лог; успешная синхронизация других файлов не снимает это предупреждение. Если диск был смонтирован, он возвращается на прежние букву и метку, в том числе после неудачного входа; при отмене lifetime повторное монтирование пропускается.
- `LogoutAsync` сериализуется с новым интерактивным входом и mount/remount/unmount. Во время выхода и смены сессии `MountAsync`/`RemountAsync` ждут завершения операции; после успешного выхода возвращают `Eng_LoginFirst`. Монтирование, уже начатое перед logout, заканчивается до его размонтирования, поэтому не оставляет диск смонтированным после выхода. Logout блокирует запуск outbox, останавливает worker, ограниченно отправляет буферизованные удаления, размонтирует диск и ещё раз отправляет удаления из `Cleanup`. Сетевой сбой не блокирует выход: недоставленные удаления снимаются с очереди, записи снова видны, ошибка указывается в `LastSyncError` и логе. Затем выполняется best-effort `Identity.Logout` с дедлайном 5 секунд и очищаются локальные токены, кеш шлюза, профиль и сохранённый `UserId`. После размонтирования удаляются пустые заготовки; заготовки с `KeepData` или содержимым сохраняются на диске с ошибкой в статусе. `GetStatusAsync` не запускает worker во время выхода, смены сессии или после logout.
- Каждая очистка кеша увеличивает эпоху аккаунта и атомарно с листингом очищает кеш каталогов. Поздние листинги, временные URL, квота и скачивания старой эпохи не публикуются; ошибка загрузки квоты не возвращает значение прежнего аккаунта. Очищаются кеши в памяти и только принадлежащие Drive файлы кеша: файл с именем GUID в формате `D` нижнего регистра, каталог `<guid>.blocks`, временный файл `<guid>.<guid:N>.part` или блоковый `<block-index>.blk.<guid:N>.part` внутри собственного каталога блоков. Каталоги `write` и `outbox` исключены; тот же предикат применяется при `ClearCache`. Удаление файлов выполняется вне блокировки эпохи.
- Если сервер отклонил `Attach` после удаления заменяемой записи, компенсирующий `RestoreFromTrash` выполняется без cancellation worker-а, чтобы остановка или logout не оставляли исходную запись в корзине. Запрос не передаёт cancellation token и ограничен стандартным gRPC deadline 30 секунд.

## Ограничения и важные детали

- Документ открыт для чтения и записи. Чтение запрашивает HTTP Range блоками по 1 МиБ и кеширует блоки в настроенной папке. Whole-режим включается только при `200 OK` на Range-запрос; `403`, `404` и `410` сбрасывают временный URL и повторяют запрос один раз, другие коды завершаются `HttpRequestException`. Перед публикацией блока сверяются `Content-Range` (единица, начало, конец и общий размер) и фактическая длина тела; скачивание целиком, включая гидрацию рабочей копии, сверяет длину с размером узла. Временные файлы `{finalPath}.{guid:N}.part` лежат рядом с целевым файлом (блоки — в `{fileId}.blocks`); собственные старые `.part` удаляются при создании `CloudGateway` и при каждой смене папки кеша. Фоновая очистка раз в минуту учитывает whole-файлы, содержимое `.blocks` и временные `.part`; лимит — 5 ГиБ и он мягкий: очистка вытесняет самые старые по `LastWriteTime` завершённые целые файлы или отдельные блоки до 80 % лимита, пропуская незавершённые `.part` и кандидатов младше минуты; поэтому временное превышение образуют скачиваемые файлы и завершённые файлы/блоки, прочитанные или скачанные за последнюю минуту. Чтения открывают кеш без `FileShare.Delete`; если артефакт вытеснен или не открылся до чтения, оно один раз повторно подготавливается при `FileNotFoundException`, `DirectoryNotFoundException` или `UnauthorizedAccessException`. Успешное открытие кеш-файла для чтения обновляет его `LastWriteTime`, если он старше 30 секунд; очистка не вытесняет кандидатов моложе минуты, поэтому порядок соответствует LRU для часто читаемых файлов. После вытеснения последнего блока пустой каталог `.blocks` удаляется. Задачи скачивания дедуплицируются, после завершения удаляется только соответствующая запись кеша задач. Путь кеша фиксируется на всё чтение; `SetCacheDir` очищает кеш задач целых файлов и блоков.
- Долгие Dokany-колбэки с `Persist`, гидрацией или фактической загрузкой данных продлевают таймаут через `IDokanFileInfo.TryResetTimeout(60_000)` каждые 10 секунд; ожидание занятого `LocalFile.Sync` в Dokan-обработчике также поддерживает keep-alive до захвата блокировки. Чтение создаёт один keep-alive при первом отсутствующем блоке и держит его до конца `Read`, а чтение из кеша его не запускает. Отказ продления записывается в лог один раз на экземпляр; таймер останавливается при завершении колбэка. Неудачная гидрация удаляет только частичный файл; `LocalFile` остаётся в реестре негидрированным, поэтому запрос можно повторить.
- `GetFileInformation` для локального файла берёт времена исходного узла; для нового локального файла используются `CreatedAt`.
- `GetDiskFreeSpace` показывает остаток пользовательской квоты: `StorageLimit - TotalUsedStorage - ReservedStorage`, а отрицательное значение ограничивает нулём. `StorageLimit=0` означает отсутствие логического лимита, тогда показывается физическая ёмкость сервера (`TotalAvailableStorage - DiskUsedStorage - S3UsedStorage`). Backend кодирует отсутствие лимита как `LimitBytes=null` → `StorageLimit=0`. `GetStorage` кеширует успешный ответ 10 секунд и объединяет параллельные RPC; у запроса дедлайн 15 секунд. При ошибке возвращается последнее значение и на 10 секунд подавляются новые запросы; без кеша ошибка передаётся вызывающему коду.
- Создание и изменение буферизуют файл во временной рабочей копии под `%TEMP%/BarkCloudDrive/write`. Реестр `LocalFile` индексируется по пути без учёта регистра; несколько хэндлов используют одну копию. Последний `Cleanup` активного хэндла загружает изменённые байты, а финальный `CloseFile` сохраняет оставшиеся изменения, включая первую paging-запись после `Cleanup`, и закрывает общий поток. Запись исключается `Sync` на всё время Persist; `MoveFile` при занятом `Sync` источника или закрытой цели возвращает `SharingViolation` без ожидания и изменяющих RPC. Перенос папки обновляет пути вложенных файлов только под `_localFilesLock`, не ожидая их `Sync`; чтение гидрированной копии и сведения о локальном файле используют `DataSync` без ожидания сети.
- Негидрированный облачный файл скачивается при первой частичной записи, записи с `WriteToEndOfFile`, чтении, `SetEndOfFile`, меняющем длину на ненулевую, или `SetAllocationSize`, уменьшающем длину ниже текущей. `SetEndOfFile` с текущей длиной и `SetAllocationSize` с размером не меньше текущего — no-op без скачивания и изменения `Modified`. Запись с нулевого смещения, покрывающая исходную длину целиком, и усечение до нуля создают локальную копию без скачивания; хвост при короткой записи сохраняется через гидрацию. Закрытие без `Modified` не вызывает `Persist` и upload; изменённый файл перед `Persist` уже гидрирован, поэтому в outbox попадают полные данные.
- `Persist` хранит сериализуемое состояние `Op` со стадией `Upload`, `DeleteOld`, `Attach` или `Done` и загруженным `FileId`. Любая новая модификация незавершённой загруженной версии сбрасывает `FileId` и стадию в `Upload`, сохраняя `OldEntryDeleted`. При неопределённом ответе предшествующего Attach его blob сохраняется в `SupersededFileId`: перед привязкой новых байтов свежий листинг позволяет удалить реально созданную прежнюю запись и избежать суффикса имени. При замене старую запись удаляют немедленным RPC после загрузки, затем привязывают новый blob с исходным именем. После неопределённого ответа `Attach` движок сверяет свежий листинг по `File.Id`; так же он находит новый `Entry.Id` для следующего сохранения. Если подтверждённая привязка исчезла из каталога, повторяется Attach того же blob с сообщением в лог; при занятой привязке вне каталога локальные данные сохраняются с ошибкой. При подтверждённом отказе привязки удалённую запись восстанавливают из корзины. Ошибка синхронизации сохраняет временные данные и видна в `EngineStatus.LastSyncError`; успешное сохранение снимает её только при пустом outbox и отсутствии предупреждения о заготовке, оставленной на диске при смене аккаунта.
- Ошибка `Persist` сохраняет `KeepData` до других действий. При последнем `CloseFile` после закрытия потока байты передаются в `%LOCALAPPDATA%/BarkCloud.Drive/outbox`: сначала в `<id>.bin`, затем атомарно записывается `<id>.json`. Манифест содержит `DirectoryId`, имя, `ExistingEntryId`, сервер/пользователя и копию `Op`; worker продолжает сохранение с сохранённой стадии с повторами через 30 с, 1, 2 и 5 мин, далее каждые 5 мин. `StopAsync` отменяет текущий проход без увеличения `Attempts`: данные и манифест остаются на текущей стадии до следующего запуска. Успех сначала удаляет манифест, затем данные; если удалить `.bin` не получилось, ошибка только логируется, файл остаётся без манифеста, а `PendingUploads` уменьшается.
- Новый пустой файл остаётся локальной заготовкой `Placeholder`, пока в него не запишут данные. После успешного сохранения содержимого это обычный `Writable`: финальный `CloseFile` удаляет рабочую копию и запись из реестра. Удаление локального файла, включая заготовку или копию после сбоя сохранения, удаляет его данные без передачи в outbox; существующая облачная запись удаляется через очередь по `ExistingEntryId`. Пустое содержимое существующего файла не заменяет облачную версию. `Pending` зарегистрирован в реестре, выдаёт локальные данные на чтение и блокирует запись, переименование и удаление.
- При помещении в outbox изменённого файла с `Op.Stage=Done` начинается новая операция `Upload`; `ExistingEntryId` сохраняется для замены текущей облачной записи.
- Для восстановления `Pending` реестр использует ключ `(DirectoryId, Name)`, поэтому локальный путь после перезапуска не требуется. Регистрация, видимость, чтение и блокировка имени ограничены текущим `ServerKey` и владельцем (при старте допустим сохранённый владелец). Если владелец при постановке неизвестен, манифест остаётся с `OwnerUserId=null` и файл скрыт: первая аутентифицированная сессия того же сервера сохраняет своего владельца в манифест и пишет событие усыновления в лог. Чужой сервер такие записи не усыновляет. `FindFiles` объединяет зарегистрированные Pending с облачным листингом; родительский каталог для поиска Pending разрешается только при непустом реестре Pending. Worker запускается после успешного входа или восстановления без ожидания сетевого прохода, только при совпадении сервера и текущего владельца; `_timerLock` атомарно защищает состояние активного прохода и запрос повтора, не допуская параллельных проходов и потерянного пробуждения. `StopAsync` отменяет и ждёт активный проход. При logout worker останавливается, видимые Pending снимаются из реестра, а открытые LocalFile временно хранятся отдельно, скрыты от новой сессии и повторно используются при регистрации того же элемента; сами записи сохраняются. При успехе сначала удаляется манифест. Если есть открытые хэндлы, файл остаётся зарегистрированным Pending, данные удаляются после последнего `CloseFile`; иначе `.bin` удаляется сразу. `.bin` без манифеста не удаляются при старте и остаются доступны в папке outbox.
- `CloseFile` для `Pending` не ждёт `Sync`, удерживаемый worker-ом во время сетевого `Persist`, и не закрывает `LocalFile.Stream`: этим потоком владеет worker и закрывает его после `Persist`. `ReadFile` открывает отдельный временный поток на один вызов. `DeletePending` у Pending не ставит `DeleteOnClose`, пока манифест существует; после удаления манифеста worker откладывает удаление `.bin` до последнего `CloseFile`.
- Удаление файла фиксируется при `Cleanup` и отправляется движком пакетно; каталоги удаляются через облачный API.
- `MoveFile` запрещает перенос `Pending` (источник и цель) и замену открытой локальной цели. Для локального нового файла путь меняется только в реестре; если заменяется облачный файл, его `EntryId` становится `ExistingEntryId`, а удаление откладывается до `Persist` после загрузки. Поэтому сбой загрузки сохраняет исходную облачную запись.
- Цель `MoveFile` ищется сначала по точному регистру, затем без учёта регистра для файлов и папок. Совпадение имени считается тем же объектом только при совпадении `EntryId` файла или `DirectoryId` папки; другая запись с похожим регистром подчиняется `replace`.
- Перемещение облачной записи при `replace=true` сначала отправляет `DeleteFileEntry` для целевого файла, затем перемещает/переименовывает источник. При одновременной смене папки и имени источник проходит через временное имя `.~bc-<8 hex>`, чтобы обойти занятые промежуточные имена. Неопределённый ответ изменяющего шага учитывается при откате как выполненный шаг; откат идёт в обратном порядке и восстанавливает цель из корзины. Ошибки отката записываются в лог, а существенные — также в `LastSyncError`; ожидаемые ответы «уже на месте» или «не найдено» остаются только в логе. Папку назначения заменить нельзя (`FileExists`); файлы и папки с одинаковым именем остаются разными серверными пространствами имён.
- Если имя цели скрыто живым тумбстоном буферизованного удаления, `MoveFile` синхронно вызывает `FlushPending` до перемещения; при сбое все неудачные пачки остаются скрытыми и возвращаются в очередь с обычным лимитом попыток. Ошибка доставки возвращается как NTSTATUS без переименования источника; после исчерпания лимита файл возвращается в листинг с ошибкой синхронизации. Это поддерживает безопасное сохранение приложениями, которые сначала удаляют старый файл, а затем переименовывают временный.
- Перенос открытого `Writable` поверх облачной записи обновляет имя, каталог и `ExistingEntryId` до возврата; если `LocalFile.Sync` занят сохранением, перенос возвращает `SharingViolation`. При переносе папки меняются ключи путей всех зарегистрированных `LocalFile` внутри неё; ID самой папки и вложенных каталогов стабильны, поэтому `DirectoryId` и ключи `Pending` `(DirectoryId, Name)` не меняются. Открытые файлы сохраняют связь с `LocalFile`, а `Persist` продолжает отправку в ту же папку уже по новому пути.
- `DeleteFile`: папка возвращает `AccessDenied`, отсутствующий путь — `FileNotFound`.
- `DeleteDirectory` сначала проверяет под блокировкой реестр `LocalFile` (включая `Pending`), затем манифесты outbox текущего сервера для этой папки: наличие любой локальной незавершённой записи сразу даёт `DirectoryNotEmpty` без RPC листинга. Это также удерживает папку, пока outbox-запись с неизвестным владельцем скрыта и ждёт усыновления сессией. Затем выполняется свежий листинг; подпапки и облачные файлы тоже дают `DirectoryNotEmpty`, а файлы, скрытые тумбстонами пользовательского удаления, считаются удалёнными. В `Cleanup` при `DeletePending` очередь удалений сначала дренируется в режиме `DropFailed`, затем проверяются реестр, outbox и свежий листинг папки: не доставленные удаления снова видны, поэтому рекурсивный RPC удаления папки не вызывается. Если папка всё ещё не пуста, причина записывается в `LastSyncError` и лог. Сам шлюз повторно дренирует очередь строгим режимом перед RPC, чтобы сбой новой пачки, добавленной между листингом и удалением, также не запускал рекурсивное удаление. Серверный `DeleteDirectory` удаляет рекурсивно; без условного удаления нельзя устранить гонку с другим клиентом, добавившим файл между проверкой и RPC.
- Повторная загрузка идентичного содержимого создаёт отдельный blob: текущая реализация backend намеренно отключает дедупликацию оригиналов. Привязка одного и того же file ID повторно не допускается; подробности модели — в [[Backend/Files]].
- RPC-ошибка при разрешении пути или листинге возвращается Dokany как NTSTATUS и не считается отсутствием пути; при такой ошибке `CreateFile` не создаёт новую рабочую копию.
- По умолчанию `DangerousAcceptAnyServerCert` и `ServerConfig.AcceptAnyCert` выключены: gRPC и HTTP transport проверяют сертификат сервера штатным валидатором платформы. Явное `AcceptAnyCert: true` в существующем `server.json` сохраняет прежнее поведение и разрешает любой сертификат. Ошибки `AuthenticationException`, включая вложенные в `HttpRequestException`, `RpcException` или `AggregateException`, показываются как ошибка защищённого TLS-соединения с подсказкой проверить адрес и сертификат либо включить доверие к любому сертификату для доверенного self-hosted-сервера; подсказка сохраняется в `LastSyncError` при сбое `Persist` и повтора outbox.
- Dokany 2.x должен быть установлен на Windows-машине. Папка рабочей копии для записи находится в системном temp; кеш скачанного содержимого настраивается отдельно.
