# Торренты в WSL2: проблема с UDP и варианты решения

## Проблема

Торрент-модуль (MonoTorrent) работает внутри WSL2 в сетевом режиме NAT. Входящий UDP-трафик (DHT-ответы на нестандартных портах, входящие uTP-подключения, входящие пиры) не доходит до WSL. Режим `mirrored` не работает / не настраивается на данной машине.

### Уточнение диагноза

WSL2 NAT блокирует только **входящий** трафик. Исходящий UDP (DHT-запросы, UDP-трекеры) и исходящий TCP к пирам должны работать — ответы возвращаются через stateful NAT. То есть скачивание (leech) должно работать даже за NAT, просто с меньшим числом пиров и без входящих подключений.

Если не качает **вообще ничего** — вероятная причина не NAT, а **Hyper-V firewall** (в Windows 11 24H2 по умолчанию режет трафик WSL) либо сам движок.

Проверка изнутри WSL: смотреть, приходят ли DHT-ответы (лог MonoTorrent, счётчик нод DHT), пробовать `curl` к HTTP-трекеру, `dig @8.8.8.8` для проверки исходящего UDP вообще.

## Вариант 1. Hyper-V firewall (быстрая проверка, часто корень проблемы)

Windows 11 (начиная с 22H2, жёстче в 24H2) имеет отдельный Hyper-V firewall, который фильтрует трафик виртуальных машин, включая WSL2.

```powershell
# Разрешить входящий трафик к WSL (GUID — стандартный для WSL)
Set-NetFirewallHyperVVMSetting -Name '{40E0AC32-46A5-438A-A0B2-2B479E8F2E90}' -DefaultInboundAction Allow
```

Плюс обычное правило Windows Firewall на порт торрент-движка:

```powershell
New-NetFirewallRule -DisplayName "BarkCloud Torrent" -Direction Inbound -Protocol UDP -LocalPort 6881 -Action Allow
New-NetFirewallRule -DisplayName "BarkCloud Torrent TCP" -Direction Inbound -Protocol TCP -LocalPort 6881 -Action Allow
```

- **Плюсы:** одна команда, не требует mirrored, после снятия блокировки часто оживает даже исходящий UDP.
- **Минусы:** не решает проблему входящих подключений извне (NAT остаётся), только внутри хоста.
- **Стоимость:** минуты.

## Вариант 2. Вынести торрент-сервис на Windows-хост (надёжный)

MonoTorrent — .NET, работает нативно на Windows. BarkCloud уже микросервисный: торрент-модуль выделяется в отдельный Windows-процесс/службу, общение с остальным беком по gRPC/HTTP (как остальные сервисы).

- **Плюсы:** полный контроль над портами, никакого NAT/WSL, самое надёжное долгосрочное решение.
- **Минусы:** работа по разделению сервиса, файлы качаются на Windows-сторону (нужен доступ к хранилищу — через `\\wsl$` медленно, лучше общая папка на NTFS или отдача файлов через API).
- **Стоимость:** часы/дни в зависимости от связанности модуля.

## Вариант 3. UDP-прокси с хоста в WSL

`netsh interface portproxy` поддерживает **только TCP** — для UDP не годится. Альтернативы:

- `socat` на Windows-стороне: `socat UDP4-LISTEN:6881,fork UDP4:<WSL_IP>:6881`
- Готовые тулзы типа `wsl2-udp-forward`

- **Плюсы:** торрент-модуль остаётся в WSL без изменений кода.
- **Минусы:** IP WSL меняется при каждом перезапуске — нужен скрипт-автообновлятор (задача в Task Scheduler при старте WSL); дополнительный движущийся элемент; socat под нагрузкой с fork на каждый UDP-пакет — сомнительная производительность для DHT.
- **Стоимость:** часы на настройку и автоматизацию, постоянная хрупкость.

## Вариант 4. VPN внутри WSL (WireGuard до VPS)

Поднять WireGuard-туннель изнутри WSL до VPS с публичным IP, на VPS пробросить торрент-порт в туннель. Весь торрент-трафик ходит через VPS, NAT Windows не участвует.

- **Плюсы:** полноценные входящие подключения, работает при любых сетевых настройках хоста, заодно скрывает домашний IP.
- **Минусы:** нужен VPS (деньги, внешняя зависимость), трафик ограничен каналом VPS, задержка.
- **Стоимость:** часы на настройку + ежемесячная плата за VPS.

## Вариант 5. Смириться с leech-only

Настроить движок на работу только с исходящими подключениями: HTTP(S)-трекеры, исходящий TCP к пирам, PEX. Отключить ожидания входящего uTP.

- **Плюсы:** ноль инфраструктурных изменений.
- **Минусы:** нет входящих пиров (медленнее на малопопулярных раздачах), раздача почти не работает (плохо для рейтинга на приватных трекерах), DHT ограниченно работает через исходящие запросы.
- **Стоимость:** только настройки движка.

---

## Рекомендация

1. **Сначала вариант 1** — одна команда, часто именно Hyper-V firewall режет всё, включая исходящий UDP.
2. Если нужен полноценный входящий трафик надолго — **вариант 2** (торрент-сервис на Windows-хосте).
