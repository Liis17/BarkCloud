# F15 · P2 — Attach успешно ссылается на уничтоженный оригинал

Срез: `d6563a2`, повторная проверка 2026-10-07. **Статус: актуален, подтверждён динамически.** Прежние исправления владения и удаления превью эту гонку оригинала не закрывают.

## Проблема и причина

[AttachFile:52](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Files/Features/Cloud/AttachFile/AttachFileCommandHandler.cs:52) берёт замок дерева владельца, затем [читает UploadFile:68](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Files/Features/Cloud/AttachFile/AttachFileCommandHandler.cs:68) и проверяет владельца/готовность. [GetFile:57](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Files/Persistence/UploadedFilesStorage.cs:57) — обычное чтение `AsNoTracking`, которое не занимает строку оригинала. Создание [CloudFileEntry:118](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Files/Features/Cloud/AttachFile/AttachFileCommandHandler.cs:118) происходит позже.

Purge не берёт тот же замок дерева. Он [удаляет строки корзины:76](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Files/Services/TrashPurgeService.cs:76), [проверяет оставшиеся ссылки:103](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Files/Services/TrashPurgeService.cs:103), [снимает владельца:136](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Files/Services/TrashPurgeService.cs:136), а затем [условно удаляет строку оригинала:226](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Files/Services/TrashPurgeService.cs:226) и вызывает S3 Delete. Attach продолжает работу по старому снимку и возвращает успех. [Модель CloudFileEntry:138](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Files/Persistence/FilesContext.cs:138) не содержит FK на `UploadFile`.

Следствие — живой элемент облака с несуществующим оригиналом: показывать/скачивать содержимое нельзя. Это подтверждённое нарушение целостности, без доказательства доступа к чужим данным.

## Доказательство

Динамика: PostgreSQL 18.6, актуальные миграции, настоящий `AttachFile` и `TrashPurgeService`, отдельные контексты. S3 — mock, физический MinIO не запускался.

Точный порядок:

1. Оригинал готов, `Uploaders=[42]`; единственная запись этого владельца уже в корзине.
2. Attach в корень читает оригинал, успешно проверяет владельца/готовность и отсутствие живой записи. Барьер останавливает его перед сохранением новой записи.
3. Purge удаляет старую запись корзины; других записей ещё нет. Он снимает последнего владельца, удаляет строку оригинала и вызывает S3 Delete.
4. Attach продолжает INSERT и commit, отвечает успешно.

```text
purge: Entries=1, Blobs=1, S3 Delete вызван
attachSucceeded=true
blobExists=false
liveEntries=1
```

`F15_AttachMustNotSucceedAfterOriginalWasPurged` **падает** на инварианте «успешная живая запись имеет оригинал». Код Attach/TrashPurge/FileOwnership не менялся от `575318a` до `d6563a2`; появились другие storage/placeholder миграции, FK этой связи не добавлен.

## Задание агенту

Исправь F15 в текущей ветке: проверка готовности/владения, добавление ссылки и решение purge об освобождении/удалении оригинала должны иметь одну согласованную границу конкурентного доступа. Начни с PostgreSQL-теста описанного порядка и его обратной очередности.

Минимальный объём:

1. Выбери одну совместную схему сериализации и примени её к **обеим** операциям. Подходит совместный owner/tree lock для Attach и DB-фазы purge либо блокировка строки оригинала с повторной проверкой владения и ссылок внутри транзакции. Объясни выбранный порядок блокировок.
2. Если используешь строку оригинала, purge должен брать блокировку **до** `stillReferenced`, а Attach — до чтения/проверки владельца и до INSERT; удерживай до commit. После ожидания нужно читать актуальное состояние, а не EF-снимок до замка. Удаление корзинных строк, решение об отсутствии ссылок и освобождение владельца должны быть согласованы с этим порядком.
3. Сохрани имеющуюся защиту orphan cleanup: условный захват строки оригинала до S3 Delete и откат при ошибке S3. Учти background purge, ручное удаление и `PurgeOrphanBlobsAsync`; не добавляй новый глобальный замок или S3-запрос в owner/tree lock без необходимости.
4. При batch purge фиксируй порядок owner/file locks, чтобы не получить взаимное ожидание; не начинай вложенные транзакции через нынешний `LockTree`. Проверь совместимость с restore, добавлением владельца при dedup и общими превью.
5. Обнови Files/vault-заметки по исправленной границе. Не переключай ветку и не меняй другие сценарии аудита.

Ловушки: обычная транзакция `ReadCommitted` вокруг Attach уже есть и не блокирует чтение оригинала. Блокировки оригинала **только в Attach недостаточно**: purge может заранее увидеть «ссылок нет», дождаться Attach commit на `RemoveUploader` и после этого удалить уже используемый оригинал. FK может служить дополнительной защитой БД, но сам по себе не согласует владение и физическое удаление S3; не заменяй им совместную границу.

## Приёмка

- Attach опередил purge: новая живая запись остаётся, владелец/оригинал и содержимое сохраняются, S3 оригинала не удаляется.
- Purge опередил Attach: Attach видит отсутствие оригинала/владения и отвечает доменной ошибкой; живой ссылки на отсутствующий или освобождённый оригинал нет.
- Между проверкой отсутствия ссылок и освобождением владельца нет окна для потерянной новой привязки.
- Проверены ручной/истёкший purge, несколько владельцев/оригиналов, совместные превью, отмена, повторный Attach и отказ S3; нет зависаний/взаимных блокировок.
- Сохранены существующие тесты restore ↔ purge и совместного превью; полный Files с PostgreSQL проходит; документация обновлена.
