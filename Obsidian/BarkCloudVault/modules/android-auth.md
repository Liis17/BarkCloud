# Android — первый запуск и авторизация

Parent: [[modules/android-app]] · Контракты: [[api/identity-api]] · [[api/users-api]] · [[modules/shared-exceptions]]

## Экраны и композиция

Нативный перенос 14 HTML-шаблонов из `Docs/New-design`, без WebView и backend-изменений:

| Шаблоны | Реализация |
|---|---|
| Три приветствия: облако, фото, обмен/офлайн | `ui/onboarding/WelcomeScreen.kt`, `WelcomeArt` |
| Сервер: адрес, порты в ряд, сертификат | `ui/server/ServerScreen.kt`, `ServerViewModel` |
| Вход паролем и ключом | `ui/login/LoginScreen.kt`, `LoginViewModel` |
| Регистрация: имя → username → почта/пароль → код → готово | `ui/auth/RegistrationViewModel.kt`, `RegistrationScreen`, `AuthSuccessScreen` |
| Сброс: логин/почта → код → новый пароль | `ui/auth/ResetPasswordViewModel.kt`, `ResetPasswordScreen` |

2FA оформлена дополнительным экраном в общей оболочке. Нативный Credential Manager не подключён: вкладка ключа объясняет ограничение и предлагает пароль. Серверный WebAuthn остаётся отдельным этапом.

`AuthScaffold` ограничивает ширину 480 dp, прокручивает формы с safe drawing/IME, уменьшает декор в низком окне. При шрифте >130% декор заголовка скрывается, порты становятся вертикальными. Основные кнопки 56/64 dp; все цвета — роли `MaterialTheme.colorScheme`, включая заголовки и декор в тёмной теме. Android 12+ использует Dynamic Color, Android 11 — текущую фирменную тему. Шрифт системный, M3-типографика с усиленными заголовками.

Общие компоненты (`ui/auth/components`): пароль с доступной кнопкой видимости и autofill, четыре сегмента надёжности, один `BasicTextField` кода с шестью визуальными ячейками, ошибки с live region, информационные карточки, countdown повторной отправки. Код фильтруется до шести ASCII-цифр; вставка и удаление работают в одном редактируемом узле TalkBack. Пароли/коды не помещаются в `SavedStateHandle` или `rememberSaveable`.

## Навигация и восстановление

`RootNavGraph`: `welcome`, `server`, `login`, `register`, `reset`, `main`. Полноценная сессия открывает main; pending-регистрация — ввод нового пароля; сохранённый сервер/сессия прежней установки пропускает приветствие. Остальные установки проходят все три страницы без кнопки пропуска. `OnboardingStore` хранит завершение последней страницы. Выход возвращает на login, сервер сохраняется. Неактивная сессия перенаправляет только из main, чтобы не прерывать pre-auth формы.

Каждая форма имеет отдельную ViewModel. При возврате внутри регистрации/сброса состояние остаётся в памяти; профиль и login дополнительно сохраняются в `SavedStateHandle`, секреты — только в памяти. После смерти процесса неподтверждённая регистрация начинается с профиля; подтверждённая pending-регистрация повторно просит пароль. Сброс повторно начинает запрос кода, не восстанавливая секреты.

App Lock остаётся оверлеем для `sessionActive`; основной граф сохранён. `MainScreen` ждёт первую запись `currentBackStackEntryFlow` перед deep-link navigate: `Scaffold` устанавливает вложенный NavHost в subcomposition, поэтому немедленный переход мог выполняться до установки графа.

## Сервер и TLS

`ServerConfig`: нормализованный адрес, Identity/Users/Files 8000/8001/8005 и `allowSelfSigned`. Адрес не содержит пути, userinfo или встроенного порта; IPv4/IPv6 поддерживаются. Порты должны быть 1–65535, невалидные значения не заменяются молча.

`ReflectionServerConnectionProbe` создаёт временный gRPC-канал для введённой конфигурации, вызывает публичный v1alpha reflection `ListServices` с deadline 5 s, проверяет ожидаемые `barkcloud.identity.IdentityApi`, `barkcloud.users.UsersApi`, `barkcloud.files.FilesApi`, закрывает канал. `ServerViewModel` запускает три проверки параллельно, показывает каждый результат, сохраняет настройки/переходит ко входу только при полном успехе. Редактирование отменяет старые проверки. Reflection подтверждает API, не состояние БД/S3/SMTP.

Для новых установок исключение сертификата выключено; старые настройки/токены мигрируют с включённым флагом. Смена адреса в форме сбрасывает флаг. Исключение проверки цепочки применяется только к выбранному хосту; стандартная проверка имени остаётся включённой. `GrpcManager` кеширует каналы с ключом конфигурации и закрывает старые после сохранения. `ServerHttpClients` выбирает TLS-политику для каждого запроса; при смене конфигурации пересоздаёт клиентов, отменяет старые запросы и очищает соединения. Этот `Call.Factory` используется Coil, FileTransfer, скачиваниями и workers. Внешние HTTPS-адреса проходят обычную проверку; клиент с исключением сертификата не следует redirect, чтобы не передать исключение другому хосту.

## Регистрация и сброс

`AuthFlowRepository` использует публичные стабы с метаданными устройства, deadline 15 s и GUID ошибок из трейлера `x-error-code`. Checked `StatusException` от gRPC Kotlin и `StatusRuntimeException` обрабатываются одинаково с сохранением trailers. `x-retry-after-seconds` задаёт срок блокировки повторной попытки; при rate limit без срока используется 60 s. Повторная отправка кода доступна не раньше 60 s и серверного срока. Неверный, истёкший/использованный код, выключенные регистрация/почта, конфликты username/email и сетевой отказ имеют отдельные пользовательские сообщения.

Username проверяется через `UsersApi.CheckExistUsername` после 400 ms, устаревшая проверка отменяется. Окончательный конфликт создания возвращает на соответствующий шаг. Новый пароль — минимум 8 Unicode-символов, максимум 72 UTF-8 байта (BCrypt); индикатор надёжности не влияет на разрешение. Эти ограничения не применяются к входу.

Цепочка регистрации: `CreateAccount → ConfirmAccount → CreateToken → SetPassword`. Если сервер сразу возвращает refresh (почта отключена), шаг кода пропускается. После подтверждения `PendingRegistrationStore` синхронно сохраняет отдельный AES-256-GCM/Keystore blob (server key, профиль, refresh, expiry); `sessionActive` ещё не включается. Blob исключён из backup/device transfer. Установка пароля использует access из pending refresh, не глобальную сессию. После успешной установки полноценные токены синхронно сохраняются до удаления pending, показывается «Готово», main открывается кнопкой.

После неизвестного результата `SetPassword` или `InvalidOldPassword` проверяется вход выбранным паролем. При возобновлении такая проверка выполняется сначала. Неверный пароль не трактуется как успех; погашенное подтверждение не отправляется повторно. Истёкший pending либо неизвестный результат самого `ConfirmAccount` требуют входа/восстановления, поскольку сервер не поддерживает повтор погашенного кода.

Сброс хранит resetId/code в памяти. Страница кода только переводит к новому паролю; `ConfirmResetPassword` одновременно отправляет resetId, код, пароль и `revokeOtherSessions` (по умолчанию true). Ошибка кода возвращает ко второму шагу. После успеха сохраняется полученная сессия и открывается main. Сообщение об отправке нейтральное, без придуманного адреса или ссылки.

Вход сохраняет текущий `Auth` и получает 2FA через `OtpRequired`; текст не утверждает конкретный источник кода. Повторный `Auth` без кода после cooldown запрашивает письмо, если аккаунт использует email OTP. Повторные запросы блокируются при loading/rate limit. Пароль/код очищаются после успеха.

## Движение и уведомления

Canvas + `graphics-shapes` дают blob/star/seal и морфинг между страницами. Появление фигур с интервалом 50 ms, плавание ±6 dp, поворот ±5° за 8–12 s выполняются через `graphicsLayer`/рисование. Циклы выключены вне RESUMED, при фокусе поля/IME и при системной длительности анимаций 0. Шаги используют те же spatial/effect-пружины Shared Axis X, что существующая навигация; способы входа — fade около 200 ms. Кнопки сохраняют ripple и сжатие .98. Завершение — однократные check/confetti около 800 ms. Действия не ждут декор.

`POST_NOTIFICATIONS` больше не запрашивается на старте. Пользовательская постановка загрузки или включение автозагрузки публикует событие `NotificationPermissionRequests`; разрешение запрашивает активная `MainActivity`/`ShareActivity`. Фоновые задания не инициируют запрос.

## Проверки и ограничения

- `testDebugUnitTest`: 77 тестов, 0 ошибок; покрыты реальные состояния ViewModel, pending/session граница, неизвестный результат установки пароля, UTF-8, rate limit и TLS с MockWebServer/self-signed сертификатом.
- `assembleDebug`, `assembleDebugAndroidTest` и `lintDebug` проходят. Lint содержит предупреждения, в том числе существующие зависимости/deprecated API и намеренный durable commit pending-состояния.
- `AuthUiTest`: 10 тестов проходят на Android 11 и Android 16; приветствие, одно поле OTP/вставка/удаление, шрифт 200%, серверная валидация, passkey fallback, возврат регистрации, сброс, доступная видимость пароля, PIN-разблокировка существующего App Lock и реальное Keystore-хранилище pending. Android 16 дополнительно проверен в тёмной теме, landscape, с системным шрифтом 200% и отключёнными анимациями.
- Opt-in `ServerReflectionIntegrationTest` запускается с `-e testServerHost https://host`; проверяет три API и публичную проверку username/отказ входа несуществующему пользователю. На `https://cloud.barkfluff.com` оба теста прошли: reflection всех трёх портов с обычным TLS, доступность свободного username и отказ несуществующему пользователю.
- Пользователь разрешил прогон на production `cloud.barkfluff.com` с отдельными тестовыми аккаунтами. `AuthBackendScenarioTest` принимает credentials только через явные runner arguments: парольный вход `codex2` через новый UI, открытие main и выход обратно на login прошли. Сброс `codex2` с реальным письмом успешно завершён через три страницы; код/новый пароль пользователь ввёл прямо в эмуляторе. `restoredSessionSupportsSettingsDeepLinkAndSignOut` подтвердил сохранённую сессию после перезапуска, чтение собственного профиля через Users, deep link в настройки и выход. Регистрация `codex3` с реальным письмом прошла всю цепочку до страницы завершения и кнопки «Начать работу». Проверены отсутствие pending после завершения, восстановление сессии, чтение профиля, deep link/выход и обычный парольный вход созданного аккаунта. Аккаунт остаётся на production для удаления пользователем. Пароли/коды в документацию не записываются.
- `AuthenticatorBackendScenarioTest`: на выделенном `codex3` временно настроен Authenticator, серверный секрет оставался в памяти теста; новый UI запросил 2FA, отверг неверный код и принял текущий TOTP, открыл main. `temporaryAuthenticatorWasRemoved` дополнительно подтвердил успешный парольный Auth и `authenticator_enabled=false` после отключения. Тест завершил сессии; пароль/секрет/коды не сохранены в исходники или отчёт. Первичный `ListOtpVerification` для аккаунта без OTP-настроек возвращает UNKNOWN/OtpNotCreated; setup guard использует успешный password-only Auth, который подтверждает отсутствие активного OTP.
- TalkBack 16.0 установлен в тестовом Android 16: во время инструментального прогона подтверждён Bound TalkBack Service; проходят OTP paste/delete, видимость пароля и достижимость действий при 200% шрифте (3 UI-теста). Семантические проверки не заменяют полный слуховой/жестовый walkthrough.
- При одном дополнительном входе на production UI-тест не дождался сессии за 25 s; следующая прямая аутентификация/чтение OTP-настроек и повторный UI-прогон входа прошли. Тест парольного входа допускает однократный повтор только при явной сетевой ошибке, credentials/OTP ошибки не маскирует.
- Полная ручная проверка TalkBack, биометрии/фонового grace period App Lock, остальных deep links и нескольких wallpaper-палитр остаётся в матрице приёмки; Email-2FA с отдельным login-письмом ещё не проверена; реальный Authenticator проверен выше. Docker/runtime инфраструктуры локально нет.

Команды из Android-проекта: `./gradlew :app:testDebugUnitTest :app:assembleDebug :app:assembleDebugAndroidTest :app:lintDebug`. Для инструментальных проверок APK устанавливались и запускались явно на `emulator-5558`/`emulator-5560`, чтобы не запускать тесты на подключённом личном телефоне.
