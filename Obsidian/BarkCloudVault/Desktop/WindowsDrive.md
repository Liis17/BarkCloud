# Windows Drive — виртуальный диск BarkCloud

Parent: [[Architecture]] · Files API: [[Backend/Files]] · Identity: [[Backend/Identity]] · IPC и proto: [[Shared/Proto]]

## Назначение

Клиент Windows монтирует облачные каталоги как диск с буквой через Dokany. Решение состоит из WPF-приложения `BarkCloud.Drive.App`, скрытого процесса `BarkCloud.Drive.Engine` и общих IPC-контрактов `BarkCloud.Drive.Contracts`.

## Публичные контракты

- UI и Engine общаются через named pipe `BarkCloud.Drive.Engine` и StreamJsonRpc. `IDriveEngine` предоставляет login/logout, обычный вход с OTP, вход WebAuthn, mount/remount/unmount, статус (`PendingUploads`, `LastSyncError`), аватар, настройки кеша, язык и shutdown.
- Движок использует отдельные gRPC-каналы Identity, Files/Cloud и Users; байты передаются по HTTP через Files web endpoint. Файлы отправляются legacy multipart-потоком; серверные операции описаны в [[Backend/Files]].
- Адрес сервера задаётся в `server.json` в профиле пользователя. Значения по умолчанию в `Drive/BarkCloud.Drive.Engine/appsettings.json`: `cloud.barkfluff.com`, Identity `:7020`, Users `:7021`, Files `:7025`.
- `EngineServerKey.FromConfig` формирует ключ из нормализованного HTTPS-адреса Identity и портов Files/Users. После входа или восстановления `UserProfile` загружает владельца через `UsersApi.GetUser(0).User.Id` и сохраняет последний известный ID в `EngineSettingsStore` по ключу сервера. Новый интерактивный вход и logout очищают этот ID до загрузки профиля; поэтому офлайн-файл при недоступном профиле получает `OwnerUserId=null`, остаётся скрытым и ждёт усыновления. При восстановлении сохранённой сессии fallback на прежний ID допустим, поскольку это тот же пользователь.
- В настройках можно менять букву диска, метку тома и папку кеша. Смена буквы/метки перемонтирует том; смена папки влияет на новые загрузки и не переносит ранее скачанные файлы.
- WebAuthn-кнопка доступна в мастере при поддержке Windows WebAuthn и доменном имени сервера. Assertion получают через Windows WebAuthn API; регистрация и управление ключами остаются вне этого клиента.

## Зависимости и взаимодействия

- `BarkCloud.Drive.App` — WPF-UI с треем и мастером первого запуска; `Engine` — `WinExe` без окна, который обслуживает Dokany и named pipe. Каждый процесс ограничен одним экземпляром на пользователя.
- `TokenManager` выполняет login и проактивно обновляет access-token через Identity. Access-token хранится в памяти; refresh-token шифруется DPAPI в `%LOCALAPPDATA%/BarkCloud.Drive/refresh.bin`. Стабильный device ID хранится рядом.
- `MetadataInterceptor` добавляет device/app headers в Base64(UTF-8), а `x-auth-token` передаёт как сырой токен. Эти метаданные нужны серверной авторизации.
- Движок восстанавливает сессию при запуске и автоматически монтирует последнюю сохранённую букву, если refresh-токен действителен. UI и Engine могут запускаться независимо через отдельные записи автозагрузки Windows.
- Список каталогов собирается cursor-пагинацией с кешем на 5 секунд. Файлы разрешаются по пути каталога; данные читаются из облака через HTTP.

## Ограничения и важные детали

- Документ открыт для чтения и записи. Чтение запрашивает HTTP Range блоками по 1 МиБ и кеширует блоки в настроенной папке; если сервер не возвращает partial response, клиент скачивает файл целиком.
- Создание и изменение буферизуют файл во временной рабочей копии под `%TEMP%/BarkCloudDrive/write`. Реестр `LocalFile` индексируется по пути без учёта регистра; несколько хэндлов используют одну копию. Последний `Cleanup` активного хэндла загружает изменённые байты, а финальный `CloseFile` сохраняет оставшиеся изменения, включая первую paging-запись после `Cleanup`, и закрывает общий поток. Запись исключается `Sync` на всё время Persist; чтение через отдельный поток и сведения о локальном файле используют короткий `DataSync`, не ожидая сети.
- `Persist` хранит сериализуемое состояние `Op` со стадией `Upload`, `DeleteOld`, `Attach` или `Done` и загруженным `FileId`. Любая новая модификация незавершённой загруженной версии сбрасывает `FileId` и стадию в `Upload`, сохраняя `OldEntryDeleted`. При неопределённом ответе предшествующего Attach его blob сохраняется в `SupersededFileId`: перед привязкой новых байтов свежий листинг позволяет удалить реально созданную прежнюю запись и избежать суффикса имени. При замене старую запись удаляют немедленным RPC после загрузки, затем привязывают новый blob с исходным именем. После неопределённого ответа `Attach` движок сверяет свежий листинг по `File.Id`; так же он находит новый `Entry.Id` для следующего сохранения. Если подтверждённая привязка исчезла из каталога, повторяется Attach того же blob с сообщением в лог; при занятой привязке вне каталога локальные данные сохраняются с ошибкой. При подтверждённом отказе привязки удалённую запись восстанавливают из корзины. Ошибка синхронизации сохраняет временные данные и видна в `EngineStatus.LastSyncError`; успешное сохранение снимает её только при пустом outbox.
- Ошибка `Persist` сохраняет `KeepData` до других действий. При последнем `CloseFile` после закрытия потока байты передаются в `%LOCALAPPDATA%/BarkCloud.Drive/outbox`: сначала в `<id>.bin`, затем атомарно записывается `<id>.json`. Манифест содержит `DirectoryId`, имя, `ExistingEntryId`, сервер/пользователя и копию `Op`; worker продолжает сохранение с сохранённой стадии с повторами через 30 с, 1, 2 и 5 мин, далее каждые 5 мин. Успех сначала удаляет манифест, затем данные; если удалить `.bin` не получилось, ошибка только логируется, файл остаётся без манифеста, а `PendingUploads` уменьшается.
- Новый пустой файл остаётся локальной заготовкой `Placeholder`, пока в него не запишут данные. После успешного сохранения содержимого это обычный `Writable`: финальный `CloseFile` удаляет рабочую копию и запись из реестра. Удаление локального файла, включая заготовку или копию после сбоя сохранения, удаляет его данные без передачи в outbox; существующая облачная запись удаляется через очередь по `ExistingEntryId`. Пустое содержимое существующего файла не заменяет облачную версию. `Pending` зарегистрирован в реестре, выдаёт локальные данные на чтение и блокирует запись, переименование и удаление.
- При помещении в outbox изменённого файла с `Op.Stage=Done` начинается новая операция `Upload`; `ExistingEntryId` сохраняется для замены текущей облачной записи.
- Для восстановления `Pending` реестр использует ключ `(DirectoryId, Name)`, поэтому локальный путь после перезапуска не требуется. Регистрация, видимость, чтение и блокировка имени ограничены текущим `ServerKey` и владельцем (при старте допустим сохранённый владелец). Если владелец при постановке неизвестен, манифест остаётся с `OwnerUserId=null` и файл скрыт: первая аутентифицированная сессия того же сервера сохраняет своего владельца в манифест и пишет событие усыновления в лог. Чужой сервер такие записи не усыновляет. `FindFiles` объединяет зарегистрированные Pending с облачным листингом; родительский каталог для поиска Pending разрешается только при непустом реестре Pending. Worker запускается после успешного входа или восстановления без ожидания сетевого прохода, только при совпадении сервера и текущего владельца; `SemaphoreSlim(1)` исключает параллельные проходы. При logout worker останавливается, видимые Pending снимаются из реестра, а открытые LocalFile временно хранятся отдельно, скрыты от новой сессии и повторно используются при регистрации того же элемента; сами записи сохраняются. При успехе сначала удаляется манифест. Если есть открытые хэндлы, файл остаётся зарегистрированным Pending, данные удаляются после последнего `CloseFile`; иначе `.bin` удаляется сразу. `.bin` без манифеста не удаляются при старте и остаются доступны в папке outbox.
- `CloseFile` для `Pending` не ждёт `Sync`, удерживаемый worker-ом во время сетевого `Persist`, и не закрывает `LocalFile.Stream`: этим потоком владеет worker и закрывает его после `Persist`. `ReadFile` открывает отдельный временный поток на один вызов. `DeletePending` у Pending не ставит `DeleteOnClose`, пока манифест существует; после удаления манифеста worker откладывает удаление `.bin` до последнего `CloseFile`.
- Удаление файла фиксируется при `Cleanup` и отправляется движком пакетно; каталоги удаляются через облачный API. Переименование и перемещение используют операции для записи каталога/файла.
- Повторная загрузка идентичного содержимого создаёт отдельный blob: текущая реализация backend намеренно отключает дедупликацию оригиналов. Привязка одного и того же file ID повторно не допускается; подробности модели — в [[Backend/Files]].
- RPC-ошибка при разрешении пути или листинге возвращается Dokany как NTSTATUS и не считается отсутствием пути; при такой ошибке `CreateFile` не создаёт новую рабочую копию.
- В конфигурации по умолчанию `DangerousAcceptAnyServerCert` включён. При активном флаге gRPC и HTTP transport принимают любой сертификат сервера; доверие к хосту не проверяется.
- Dokany 2.x должен быть установлен на Windows-машине. Папка рабочей копии для записи находится в системном temp; кеш скачанного содержимого настраивается отдельно.
