# F22 · P2 — Pause/Resume движка расходятся с `Paused` в БД

Статус на 2026-10-07: **актуален, воспроизведён**. Проверенный срез: `d6563a2`. Код Torrent и его штатные тесты не менялись относительно `575318a`.

## Задание агенту

Согласуй полную операцию Pause/Resume одного торрента: проверку владельца и чтение актуального состояния, действие движка, сохранение `Paused` и восстановление после отказа БД. Сохрани параллелизм разных торрентов. Ограничь scope этим сценарием и нужными регрессионными тестами; не переписывай весь `TorrentApiService`. Работай в текущей ветке; обнови заметку `Obsidian/BarkCloudVault/modules/backend-torrent.md` после изменения поведения.

## Где и почему ломается

[PauseTorrent:282](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Torrent/Host/TorrentApiService.cs:282) читает сущность, вызывает `_engine.PauseAsync`, затем отдельно меняет `entity.Paused` и вызывает `_store.SaveChanges`. [ResumeTorrent:292](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Torrent/Host/TorrentApiService.cs:292) делает симметричные шаги.

В [TorrentEngineService.cs:153](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Torrent/Infrastructure/TorrentEngineService.cs:153) `RunExclusiveAsync` удерживает `ManagedTorrent.Gate` только вокруг действия MonoTorrent; [строка 169](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Torrent/Infrastructure/TorrentEngineService.cs:169) освобождает замок до записи флага в БД. Поэтому порядок действий движка не определяет порядок сохранений БД.

Дополнительная деталь: [TorrentStore.Get:40](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Torrent/Persistence/TorrentStore.cs:40) возвращает tracked-сущность, а [SaveChanges:56](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Torrent/Persistence/TorrentStore.cs:56) использует обычный EF change tracking. Запись того же `false`, которое было прочитано ранее, вообще не создаёт `UPDATE Paused`, даже если другой запрос уже сохраняет `true`.

## Минимальная гонка

Исходно `DB.Paused=false`, движок работает. Два RPC имеют отдельные scoped-контексты.

1. A/Pause читает `false`, успешно приостанавливает движок и освобождает engine gate.
2. A меняет tracked-флаг на `true`, но задерживается перед сохранением БД.
3. B/Resume читает прежнее `false` из БД, успешно запускает движок. Присваивание `false` не отличается от исходного значения tracked-сущности; `SaveChanges` не записывает флаг.
4. A сохраняет `true`.

Оба RPC успешны. Последнее действие движка — Resume, но `DB.Paused=true`. Даже простое расширение замка только на действие движка и `SaveChanges` не полностью исправит проблему, если `RequireOwned`/чтение tracked-сущности останется снаружи: ожидающий RPC может войти с устаревшим исходным флагом.

## Отдельный сценарий отказа БД

Один Pause успешно приостанавливает движок. Затем `SaveChanges` падает до commit. RPC возвращает ошибку, в БД остаётся `Paused=false`, движок остаётся приостановленным. Компенсации или последующего согласования нет. Для Resume возможен обратный эффект: торрент качает после неудачного сохранения `Paused=false`, а в БД остаётся `true`.

## Влияние

После рестарта состояние меняется неожиданно для пользователя: [TorrentStartupService.cs:46](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Torrent/Infrastructure/TorrentStartupService.cs:46) запускает торрент по `!entity.Paused`. Успешный Resume может потеряться после рестарта; успешно остановленный движок может автоматически запуститься. Ошибка БД оставляет неоднозначный результат RPC: клиент получил ошибку, но движок уже изменился.

## Минимальное исправление и ловушки

- Использовать общий **замок одного torrent ID** для полного сценария, совместимый с текущими Pause/Resume/Remove. Читать/перечитывать owned-сущность внутри этой границы и сохранять актуальный флаг до освобождения замка. Не брать глобальный замок на все торренты.
- Не вызывать текущие `PauseAsync`/`ResumeAsync`, повторно захватывающие тот же `SemaphoreSlim`, из уже захваченного gate: это создаст deadlock. Нужен внутренний путь действия движка без повторного захвата либо операция с callback сохранения, остающаяся под существующим gate.
- Одновременно определить политику отказа БД. Для сохранения нынешнего порядка «движок → БД» при подтверждённом откате восстановить прежний режим движка под тем же замком и вернуть клиенту ошибку. Простая сериализация без компенсации не закрывает второй сценарий.
- Если commit мог пройти, а подтверждение потерялось, нельзя безусловно откатывать движок к старому флагу: сначала выяснить persisted-состояние через свежий контекст. Когда БД/компенсация недоступна, ошибка должна оставлять явную задачу повторного согласования, а не ложный успех; повторное согласование не должно отменить более позднюю успешную команду. Зафиксировать, какое persisted-состояние считается источником истины.
- Глобальная атомарность БД и MonoTorrent одним EF-транзакционным commit невозможна. Для восстановления после аварии процесса использовать persisted-флаг как состояние запуска; не обещать атомарность внешнего движка, которой нет.
- Ограничить ожидание gate/восстановления и передавать отмену RPC в новые пути. Не удерживать замок разных торрентов во время медленной БД.
- После ожидания замка заново проверять, что торрент всё ещё существует и принадлежит пользователю; не возвращать успех Pause/Resume для уже удалённого менеджера лишь из-за текущего no-op в engine wrapper.

## Критерии приёмки

1. С барьерами воспроизвести `Pause → Resume` и `Resume → Pause` на отдельных scoped-контекстах; после обоих успешных RPC флаг БД соответствует последнему действию движка.
2. Отдельно проверить RPC, прочитавший сущность до завершения предыдущего RPC: stale EF original value не должен потерять запись нового флага.
3. Отказ БД до commit после успешного engine-действия восстанавливает прежний режим либо приводит к явному контролируемому повторному согласованию; исключение не маскируется успехом.
4. Проверить отказ самого движка, отказ компенсации и неизвестный результат commit. После восстановления зависимостей БД и движок сходятся; поздняя успешная команда не отменяется старым retry.
5. Pause/Resume против Remove не создают ложный успех или восстановление удалённого менеджера; две операции разных torrent ID не блокируют друг друга.
6. После рестарта используется согласованный persisted-флаг. Штатные Torrent-тесты проходят; обновлено описание границы операции и политики отказа в vault.
