## High

### 1. Stored XSS через image-proxy и SVG

**Где:** `Backend/BarkCloud.Web/WebEndpoints.cs:61-96`, `Backend/BarkCloud.Files/Extensions/FileExtensions.cs:26`, `Backend/BarkCloud.Files/Features/DownloadFile/DownloadFileCommandHandler.cs:85-90`.

`/api/files/image` анонимен. Он берёт GUID из любого URL, содержащего `/download/`, загружает `/download/{id}` с внутреннего Files и отдаёт тело на origin веба с `Content-Type` из ответа upstream. Files определяет MIME по расширению имени файла: `.svg` → `image/svg+xml`. Тип загружаемого содержимого задаёт клиент, поэтому SVG можно загрузить в обход обработки ImageSharp. Ответ прокси не содержит `Content-Disposition: attachment`, `X-Content-Type-Options` и CSP. CSP нет и у веба в целом.

**Сценарий:** злоумышленник загружает `evil.svg` со `<script>`, создаёт публичную ссылку и берёт временный GUID из `/s/{token}/info` (`downloadUrl`). Жертве отправляется ссылка `https://<host>/api/files/image?url=https://x/download/<guid>`. Скрипт выполняется на origin BarkCloud Web. Его `fetch('/api/...')` уходят с cookie жертвы: `SameSite=strict` не мешает запросам с того же origin. Через них можно читать и расшаривать файлы, менять настройки, а при разблокированном AdminGate — управлять Docker-обслуживанием.

**Исправление:** в прокси разрешить только растровые типы (`image/jpeg|png|webp|gif|avif`) и отклонять `image/svg+xml`. Добавить `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox; default-src 'none'` и `Content-Disposition: inline; filename=...`. Глобально — задать CSP для SPA.

### 2. Apple-клиенты по умолчанию не проверяют TLS-сертификат

**Где:** `Mac/BarkCloudKit/Sources/BarkCloudKit/Networking/GrpcManager.swift:41,80,264-266`, `.../InsecureURLSession.swift`, `Ios/BarkCloud/BarkCloud/Features/ServerSetup/ServerSetupScreen.swift:21`, `Mac/BarkCloudDrive/BarkCloudDrive/ServerSetupView.swift:14`.

В `ServerConfig.production` указано `allowSelfSigned: true`. На экране настройки iOS переключатель по умолчанию `true`, macOS наследует значение по умолчанию. В режиме `allowSelfSigned` gRPC использует `.noVerification`, а HTTP — делегат, который принимает любой trust для `filesHost`. Это не «доверие self-signed», а полное отключение проверки: подойдёт любой сертификат.

**Последствие:** злоумышленник в той же сети (публичный Wi-Fi, подменённый DNS) перехватывает логин/пароль, OTP, `x-auth-token`, refresh-токены и файлы.

**Исправление:** значение по умолчанию — `false`. Вместо `.noVerification` закреплять отпечаток сертификата, подтверждённый пользователем при первом подключении (TOFU pinning), и показывать предупреждение. Для существующих установок — миграция с повторным запросом согласия.

## Medium

### 3. Email-сброс пароля обходит Authenticator

**Где:** `Backend/BarkCloud.Identity/Features/ResetPassword/ResetPasswordCommandHandler.cs:133-176`, `.../ConfirmResetPassword/ConfirmResetPasswordCommandHandler.cs:163-245`.

Тип OTP для сброса выбирает клиент. Ветка `Email` не проверяет, включён ли у аккаунта Authenticator. `ConfirmResetPassword` после проверки кода из письма меняет пароль и **сразу выдаёт access/refresh-сессию**. При входе (`AuthCommandHandler.cs:159-243`) TOTP обязателен, а при сбросе — нет. Доступа к почтовому ящику достаточно, чтобы захватить аккаунт с включённой 2FA.

**Исправление:** если у аккаунта включён Authenticator, требовать TOTP вторым фактором и при сбросе по email. Либо после сброса не выдавать сессию: следующий вход тогда пройдёт обычную проверку 2FA.

### 4. TOTP: нет защиты от повтора, TOTP-сброс однофакторный

**Где:** `VerifyTotp(..., out timeStepMatched, ...)` в `Auth`, `ConfirmResetPassword`, `ConfirmOtpVerification`, `DisableOtpVerification`, `EnableOtpVerification`. `timeStepMatched` нигде не сохраняется.

Принятый при входе код повторно действителен ~90 с (окно `RfcSpecifiedNetworkDelay`) в любом другом потоке. Для сброса с `OtpType=Authenticator` нужны только логин и текущий TOTP, пароль не требуется. Код, подсмотренный или перехваченный фишинг-прокси при входе, позволяет сменить пароль и получить сессию.

**Исправление:** хранить последний принятый `timeStep` на аккаунт и отклонять `<=` (атомарно в БД). Для сброса через Authenticator дополнительно требовать email-код.

### 5. Passkey без повторной аутентификации

**Где:** `Backend/BarkCloud.Identity/Features/BeginWebAuthnRegistration/*`, `CompleteWebAuthnRegistration/*`, `RemoveWebAuthnCredential/*`.

Регистрация и удаление passkey требуют только действующую User-сессию: без пароля и OTP (`ReauthPasswordVerifier` используется только для OTP и смены пароля), без уведомления по почте. `ConfirmResetPassword` и «отозвать все сессии» не удаляют WebAuthn-ключи. Украденная на время сессия (XSS из п. 1, утёкший токен) превращается в постоянный беспарольный вход, который переживает смену пароля.

**Исправление:** требовать повторную аутентификацию (пароль/OTP) для Begin/Remove. Отправлять письмо о добавлении ключа. Предлагать или выполнять удаление passkey при сбросе пароля.

### 6. SMTP с отключённой проверкой сертификата по умолчанию

**Где:** `Backend/BarkCloud.Configuration/Infrastructure/ConfigurationDefaultsPopulator.cs:190-191`, `Backend/BarkCloud.Notification/Senders/EmailSender.cs:41-42`.

Значение по умолчанию `Email:AllowInsecure = "true"`, и при `true` колбэк принимает любой сертификат. MITM между Notification и SMTP-сервером перехватывает учётные данные отправителя и содержимое писем, включая коды сброса пароля и входа.

**Исправление:** по умолчанию `false`. Для self-hosted SMTP — явное включение или закрепление отпечатка сертификата.

### 7. Android: миграция включает `allow_self_signed`

**Где:** `Android/.../grpc/ServerSettings.kt:56-63`, `GrpcManager.kt:111`, `net/InsecureTls.kt`.

Если ключ отсутствует, а в настройках есть любые прежние данные (настройки сервера, токен), при обновлении приложения записывается `allow_self_signed=true`. Тогда `InsecureTls` отключает проверку цепочки для всех authenticated gRPC-каналов. Новые установки не затронуты.

**Исправление:** мигрировать в `false` и спрашивать пользователя только при ошибке проверки сертификата (с pinning).

### 8. Windows Drive: устаревший `AcceptAnyCert`

**Где:** `Drive/BarkCloud.Drive.Engine/Program.cs:70`, `BarkCloudConnection.cs:51`, `TokenManager.cs:119`.

Строгий TLS поменял значения по умолчанию, но не мигрировал сохранённый `server.json`. Сохранённое `AcceptAnyCert=true` по-прежнему отключает проверку для gRPC и HTTP, и refresh-токен уходит при автоматическом восстановлении сессии. Нужно проверить на реально обновлённой установке.

**Исправление:** одноразовая миграция `AcceptAnyCert → false` с повторным согласием или pinning.

### 9. Общие секреты на все сервисы (defense in depth)

**Где:** `Backend/BarkCloud.GrpcServer/XAuth/XAuthExtensions.cs:20`, `Backend/BarkCloud.Web/Infrastructure/ServiceToken.cs`, `Backend/BarkCloud.Configuration/Infrastructure/ConfigurationAccessInterceptor.cs`, `Backend/docker-compose.yml:7`.

- Все сервисы проверяют JWT одним симметричным HMAC-ключом, поэтому каждый может выпустить **любой** User- или Service-токен. Политика `Service` проверяет только `token_type`. `IdentityServerApi.CreateSessionForUserServer` выпускает сессию для произвольного `UserId` и в коде не вызывается. Отдельно этот кандидат не засчитан: он поглощается общей проблемой ключа.
- `CONFIGURATION_ACCESS_KEY` один на все сервисы, а `GetAll` отдаёт все секреты всех сервисов. Если ключ не задан, Configuration API работает **без аутентификации** (fail-open с предупреждением в логе).
- RabbitMQ: письма с кодами сброса проходят через общую шину. `EmailQueueConsumer` не проверяет отправителя, ACL очередей в репозитории не заданы.

Компрометация любого одного контейнера (например, Torrent, который обрабатывает недоверенные торренты) означает компрометацию всего облака.

**Исправление:** асимметричная подпись (Identity подписывает, остальные проверяют по публичному ключу), отдельные сервисные идентичности со скоупами. Configuration должна отдавать сервису только его раздел. При пустом ключе Configuration — fail-closed.

### 10. Builder: известные учётные данные инфраструктуры

**Где:** `Tools/BarkCloud.Builder/BuilderModel.cs:53-66`, `BuilderModelValidator.cs`, `BackendComposeGenerator.cs:242,938`.

MinIO/RabbitMQ/Postgres получают `user`/`password`, Seq — тоже значения по умолчанию. Случайными генерируются только ключ Configuration и админ-пароль Web. Валидатор не проверяет стойкость паролей. Порты БД/MinIO наружу не публикуются, но при включённых `NginxMinioConsoleProxy`/`NginxSeqProxy` консоль MinIO с `user/password` доступна извне.

**Исправление:** генерировать все пароли так же, как `ConfigurationAccessKey`. Валидатор должен запрещать известные значения.

### 11. Icon-proxy и `X-Forwarded-Host` (условно)

**Где:** `Backend/BarkCloud.Web/WebEndpoints.cs:28-53,268-310`, `Program.cs:150-157`.

Анонимный `/api/head/icon` разрешает целевой хост, равный `App:PublicHost`, а если тот пуст — `Request.Host`. `ForwardedHeaders` доверяет `X-Forwarded-Host` от любого источника (`KnownProxies/KnownNetworks` очищены), nginx передаёт `$host` клиента. При пустом `WEB_PUBLIC_HOST` анонимный пользователь заставляет Web выполнить GET на любой хост, включая внутренние, с путём `/download/`. Это blind SSRF с ответом для `image/*`. В `sample.env` и Builder значение задано, поэтому риск возникает только при ошибке конфигурации.

**Исправление:** без `App:PublicHost` прокси отключать. Ограничить `KnownNetworks` подсетью docker.

## Low

12. **Users — утечки профиля** (`Backend/BarkCloud.Users/...`):
    - `CheckExistEmail` анонимен (`UsersApiService.cs:63`) и раскрывает регистрацию email. Сброс пароля, напротив, это скрывает, а у Users на nginx нет rate limit.
    - `GetUser` по произвольному ID возвращает черновики (`UsersStorage.GetById` без `IsDraft`).
    - `ProfileVisibility` сохраняется, но **нигде не применяется** в `SearchUsers`/`GetUser`.
    - `UserMapping` отдаёт чужой `StorageLimitGb`.
    - Имена без ограничения длины: несколько аккаунтов с именами ~1 МБ могут превысить 4 МБ ответа `SearchUsers` (правдоподобно, не воспроизведено).
13. **AdminGate** (`Backend/BarkCloud.Web/Auth/AdminGate.cs`): cookie подписывает только срок, не привязана к пользователю/сессии и не удаляется при `LogoutAsync`. Следующий пользователь того же браузера в течение 30 минут получает доступ к обслуживанию. Кроме того, общий лимит разблокировки (20/час, `AdminUnlockLimiter`) тратит любой авторизованный аккаунт до проверки пароля и так может заблокировать администратора.
14. **Аватар:** `ReadFormAsync` разбирает тело до проверки 10 МБ, а лимиты отключены во всех слоях (`MaxRequestBodySize=null`, `MultipartBodyLengthLimit=long.MaxValue`, `client_max_body_size 0`). Авторизованный пользователь заполняет временный диск Web. Старые аватары не удаляются и не учитываются в квоте.
15. **Files — квоты и DoS:**
    - `CreateArchive` не проходит квоту (архив в корзине 3 дня учитывается сверх лимита) и не передаёт `context.CancellationToken`.
    - Upload 2.0 ограничивает только байты, не число сессий: при безлимитной квоте можно открыть сколько угодно multipart-загрузок.
    - Legacy `GetUploadUrl` создаёт placeholder-строки без очистки.
    - После удаления аккаунта upload-токен сессии продолжает принимать части и продлевать `ExpiresAt`.
16. **Временные ссылки** живут 60 минут (`TempFiles:ExpiresAt`) и не отзываются при удалении папки или отзыве доступа. Это bearer-ссылки по дизайну; учитывайте при отзыве.
17. **Гонки с финальной очисткой корзины** (правдоподобно, не воспроизведено): создание share во время purge, выдача ссылки на трек плейлиста, удалённый параллельно.
18. **Torrent:**
    - Нет квоты на объём загрузки, общий том можно заполнить.
    - URL трекеров из magnet/.torrent уходят в MonoTorrent без политики назначения: blind SSRF через announce на внутренние адреса.
    - `UserDeletedConsumer` проглатывает ошибку удаления каталога и удаляет строки, поэтому повторной очистки не будет.
    - Поиск материализует все строки пользователя (влияет только на свой аккаунт).
19. **Отзыв токенов fail-open:** при недоступности ленты отзывов реплики продолжают принимать отозванные токены, пока не восстановится синхронизация (максимум — срок жизни access-токена, 60 мин). Это осознанный компромисс доступности; стоит добавить метрику или алерт о возрасте кэша.
20. **Подменяемый `x-ip-address`:** `RequestContext.IpAddress` берётся из метаданных клиента и попадает в логи (переводы строк в консольном Serilog не экранируются) и в письма безопасности (IP и местоположение подменяются). Лимиты попыток не затронуты: они используют доверенный `SourceIpResolver`.
21. **iOS-виджеты:** `TrashWidgetBridge` не очищается в `resetLocalState()`, и число объектов и дата очистки корзины видны после выхода. При перемещении в сейф (`moveSelectedToVault`) не обновляется `RecentMediaWidgetBridge`, и фото остаётся на виджете до следующей перезагрузки ленты.
22. **Windows Drive:**
    - Legacy refresh-токен без привязки к серверу помечается текущим `ServerKey` и может уйти на другой сервер.
    - Записи outbox без владельца при входе переходят к следующему аккаунту.

    Требуется проверка в рантайме.
23. **Supply chain:** Files копирует ffmpeg/ffprobe из `mwader/static-ffmpeg:latest` без digest. Lognara-agent проверяется контрольной суммой, скачанной из того же источника. Рекомендуется закрепить digest.
24. **ImageSharp:** проверяется число пикселей холста, но не число кадров анимации. Риск исчерпания памяти на анимированных GIF/WebP не подтверждён.

## Отклонено / не подтверждено

- **Android ShareActivity** — независимая проверка отклонила: файл попадает только в собственный аккаунт пользователя, путь утечки к отправителю не найден.
- **Torrent path traversal в fallback `TorrentController.Download`** — `Path.Combine` без проверки containment действительно есть. Но MonoTorrent.Client отвергает пути с `/../` и `\..\`, а при ошибке добавления запись удаляется (`_store.Remove`). Рабочий путь не найден. Оставить как hardening: проверка `GetFullPath(...).StartsWith(SavePath)`.
- **`IdentityServerApi.ServiceTokenScope`** — самостоятельно не засчитан, учтён в п. 9.

2. пп. 3–5 — усилить сброс пароля, TOTP и passkey.
3. пп. 6–8 — значения TLS по умолчанию и миграции в Notification, Android и Drive.
4. пп. 9–10 — разделение секретов и генерация паролей в Builder (архитектурная работа).
5. Остальное — по мере работы в соответствующих компонентах.
