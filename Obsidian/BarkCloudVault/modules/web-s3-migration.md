# Миграция бакета S3

Parent: [[modules/web-settings]] · See also: [[modules/backend-configuration]] · [[modules/backend-files]] · [[modules/web-system-updates]] · [[api/web-s3-migration-api]] · [[api/configuration-api]] · [[api/files-api]]

## Интерфейс и жизненный цикл

Последняя вкладка настроек — `/settings#migration`, доступная только после административной разблокировки. `MigrationTab` использует MD3 Select, Switch и токены обеих тем: две равные карточки на широком экране, вертикальные карточки со стрелкой вниз на узком. Поиск настроек индексирует названия полей и действий, без значений секретов.

Источники включают активные и прошлые версии, а также legacy-профили. Фактический endpoint из S3Endpoint.Normalize и bucket определяют физическую группу (R2 HTTP/HTTPS и нестандартные порты объединяются после HTTPS override); роли и все `ProfileId` видны отдельно. Назначение содержит endpoint, bucket, credentials, Region, ForcePathStyle и IsR2. Изменение любого поля или источника отменяет проверку. После запуска введённые ключи очищаются; браузерные хранилища не используются.

Endpoint назначения можно вводить без протокола: `MigrationTab` убирает пробелы по краям и добавляет `https://` при уходе из поля и перед запросом проверки. Явный `http://` сохраняется, в том числе для локального S3 с портом. Некорректный адрес (другой протокол, credentials, query или fragment) отмечается рядом с полем через подсказку и `aria-invalid`, поэтому отключённая кнопка проверки имеет видимую причину.

`MigrationProgress` показывает этап, полные ключи, подтверждённые байты/файлы, текущий файл и процент. SVG-индикатор имеет активную волну, дорожку и stop indicator; `prefers-reduced-motion: reduce` выключает движение. `useStorageMigration` получает состояние раз в секунду только в активной видимой панели и сразу обновляет его при возвращении. При скрытии вкладки незавершённый polling отменяется; запоздалые ответы не заменяют свежие данные. Закрытие страницы не отменяет серверную работу.

## Копирование в Web

`StorageMigrationService` — singleton BackgroundService с одним worker и одной выполняющейся задачей. Проверка хранит credentials и привязку к источнику в памяти сервера на 15 минут, возвращая только непрозрачный `validationId`. Запуск принимает этот ID, а не новое подключение.

`S3MigrationCopier.CheckAsync` проверяет существование и доступность назначения, записывает уникальный объект `.barkcloud-migration-check/<uuid>`, читает и проверяет SHA-256, затем удаляет конкретную версию и проверяет удаление. Неудачная очистка запрещает запуск. Непустое назначение разрешено для продолжения после рестарта; копирование в себя и в уже используемый BarkCloud бакет запрещено. Тест доступа не изменяет существующие пользовательские объекты.

Перечисление идёт через ListObjectsV2 по всем страницам без Prefix/Delimiter. Инвентарь и подтверждённые результаты пишутся во временные NDJSON-файлы. Ключи сохраняются буквально. Сохраняются Content-Type, Content-Disposition, Content-Encoding, Content-Language, Cache-Control, Expires и пользовательские metadata. Источник использует только GET/HEAD/LIST.

Перед загрузкой `InspectExistingAsync` проходит весь инвентарь и вызывает `VerifyExistingAsync` для имеющихся ключей назначения. Совпадения подтверждаются по размеру, metadata, значимым заголовкам и SHA-256 полного содержимого источника и копии; разные ETag двух серверов не мешают совпадению. Подтверждённые копии сразу учитываются в прогрессе и записываются в `inspected.ndjson`; недостающие или отличающиеся объекты загружаются после завершения этого прохода. Посторонние ключи назначения не удаляются. Проверка существующих копий требует чтения данных и на медленной сети может занять длительное время, хотя повторной загрузки нет.

Объекты до 64 МиБ передаются PutObject через временный файл; более крупные — multipart, с буфером на диске только для одной части. Размер части увеличивается при необходимости уложиться в 10 000 частей. Каждая часть читается отдельным условным Range GET: соединение источника закрывается до загрузки части, поэтому не простаивает часами во время передачи на другой S3. После полностью прочитанной части её байты добавляются в SHA-256; копия читается диапазонами по 64 МиБ и сверяется по размеру, SHA-256, metadata и заголовкам. ETag закрепляет версию содержимого при чтении диапазонов, не является универсальным хешем.

У S3-клиентов миграции `HttpClient.Timeout` — 30 минут до заголовков ответа (для upload включает передачу части), подключения — 30 секунд; общего дедлайна на файл нет. После получения заголовков при чтении действует таймер отсутствия данных 5 минут, сбрасываемый после каждого блока. IOException/HttpRequestException/TimeoutException, клиентский таймаут без отмены задачи, HTTP 5xx и S3 RequestTimeout повторяют текущий диапазон до трёх попыток с задержкой 1/2 с, очищая частичный буфер. Уже загруженные части и SHA-256 не учитываются повторно. В интерфейсе отдельно видны `checking-existing`, `reading` и `final-reading`.

Прогресс фиксируется только после проверки, включая совпавшие существующие копии. Ошибка сохраняет подтверждённые счётчики и незавершённый объект; продолжение обрезает недописанный хвост манифеста проверки/копирования и повторяет объект без двойного учёта. Multipart прерывается при ошибке; его ID сохраняется во временном checkpoint, чтобы повторить очистку при потерянном ответе. NoSuchUpload/404 означает уже выполненную очистку. LastModified сохраняется из ListObjects, поскольку HTTP-заголовок теряет доли секунды. Исчезнувший объект живого источника пропускается, а отсутствие копии при проверке останавливает задачу.

`Fail` пишет тип исключения, HTTP-статус и код S3 из фиксированного списка. Исходный текст SDK-исключения и сам объект исключения не логируются; credentials не попадают в ответы. Безопасный статус и известный S3-код также включаются в сообщение интерфейса, а обрыв сети и таймаут имеют отдельные объяснения.

## Применение

`MigrationApplyPanel` в основных S3-настройках показывает «Применить миграцию» и существующий ConfirmModal с назначением и всеми затрагиваемыми профилями.

1. Проверить preflight обслуживания для Files, затем актуальность исходных профилей.
2. Через FilesServerApi установить `StorageCutover` в `draining`: запретить новые admission, дождаться Uploading/Processing/CleanupPending (включая сессии с отдельным бакетом превью фото, видео и аудио), legacy HTTP upload и обработки аватаров.
3. Эксклюзивный advisory lock дожидается выполняющихся S3-изменений и переводит бакет в `frozen`. Все изменения через S3Uploader/S3MultipartUploadStore блокируются, чтение продолжается.
4. Новый NDJSON-инвентарь сверяется потоково с подтверждённым манифестом. Объекты с неизменившимися ETag, размером и LastModified дополнительно сверяются через HEAD по хешу metadata и значимых заголовков; неизменившиеся пропускаются без повторной передачи; новые/изменённые копируются и проверяются.
5. До сохранения можно отменить переключение. Web сначала проверяет, что Configuration всё ещё содержит всю исходную группу, затем снимает барьер. Ошибка сверки не меняет конфигурацию.
6. Барьер получает `applying`; отдельный RPC Configuration атомарно заменяет подключение всех исходных профилей, сохраняя ID, версии, роли, активность, legacy и квоты, с ревизиями MigrationRelocation.
7. Через общую очередь DeploymentJobService перезапустить Files и проверить `applied`. Files выставляет это состояние только после загрузки всех новых подключений и совпадения SHA-256 подключения, включая credentials; хеш не возвращается в статусах. Ошибка перезапуска допускает повтор, сохраняя запрет записи на старый S3.

Барьер хранится в БД Files независимо от временной Web-задачи. `StorageWriteActivities` учитывает legacy HTTP-body и аватарные pipelines; PostgreSQL lifetime advisory lock позволяет отличать живые операции от оборванных после рестарта, не удаляя активности другой живой реплики. После рестарта Web UI основных S3-настроек получает незавершённые барьеры: предлагает безопасную отмену при прежних подключениях либо повтор перезапуска при уже сохранённом назначении.

## Ограничения

Назначение выделяется исключительно для миграции и создаётся заранее. Копируются текущие объекты, без history, ACL, policy и lifecycle. Внешние приложения не должны изменять бакеты во время переключения. Временная задача не восстанавливается после рестарта Web: повторная проверка подключения и новая задача с тем же назначением заново сверяют завершённые копии и передают оставшиеся объекты. Незавершённый multipart-файл после рестарта передаётся с начала; его части не восстанавливаются, а осиротевшие multipart uploads следует очищать lifecycle назначения. Исходные объекты не удаляются. Применение выполняется отдельно от основного копирования.

## Проверки

Backend: `S3MigrationCopierTests`, `StorageMigrationServiceTests`, `StorageMigrationEndpointsTests`, `StorageMigrationGateTests`, `StorageMigrationGatePostgresTests`, `StorageProfileStorageTests`. Frontend: `MigrationTab.test.tsx`, `SettingsPage.test.tsx`, `ServerSettingsTab.test.tsx`.

Для сетевого интеграционного теста двух тестовых S3 задать `BARKCLOUD_MIGRATION_SOURCE_ENDPOINT`, `BARKCLOUD_MIGRATION_TARGET_ENDPOINT` и тестовые `BARKCLOUD_MIGRATION_ACCESS_KEY`/`BARKCLOUD_MIGRATION_SECRET_KEY`, затем запустить `S3MigrationIntegrationTests`. Тест создаёт собственные случайные бакеты и очищает только свои fixtures.

`S3MigrationLargeObjectTests` запускается отдельно с `BARKCLOUD_MIGRATION_LARGE_TEST=1`: генерирует полный поток 22 ГиБ + 3 байта, передаёт и хеширует 353 части, проверяет Int64-диапазоны и SHA-256 записанных байтов. На диске хранится только часть до 64 МиБ. Этот тест использует SDK-моки и не воспроизводит десятичасовое соединение с реальным провайдером.

Проверено 2026-10-03 на двух независимых локальных MinIO: versioned cleanup, 65 МиБ multipart, вложенные Unicode/спецсимволы, metadata, Content-Encoding/Content-Language/Expires, SHA-256, range, новые/изменённые объекты и final sync без повторной передачи неизменившегося multipart. PostgreSQL 17 подтвердил межрепличные advisory leases, lifetime активности и отсутствие deadlock при аварийном Abort.

Итоговый прогон: Configuration 76, Files 563 (с PostgreSQL), Web 174 (с двумя MinIO), GrpcServer 68; frontend 131 и production build/typecheck. EF не обнаружил расхождения обеих моделей с последними миграциями. Backend/Shared/Tests собираются на macOS; общий BarkCloud.slnx включает Windows-проекты Drive/Builder и требует Windows targeting. Реальный Docker restart в этой среде не запускался (Docker CLI отсутствует); переходы барьера, загрузка нового registry и сбои перезапуска проверены тестами.

После падения CI повторён прогон Files на PostgreSQL 18 с обязательным SCRAM-паролем: до исправления три `StorageMigrationGatePostgresTests` падали из-за потери пароля при копировании строки подключения, после передачи исходного `NpgsqlDataSource` полный набор прошёл 563/563 без пропусков. Требования к этой фикстуре и отличие от локального `trust` — [[structure/testing#PostgreSQL-тесты Files]].

Проверено 2026-10-04: Web 183/183 без пропусков (два независимых MinIO и включённый полный поток 22 ГиБ + 3 байта), frontend 139/139, typecheck и production build. Сетевой тест подтверждает повторный check/start новым Web worker в непустой versioned бакет без новых версий совпавших объектов, затем final sync новых/изменённых объектов. Регрессии покрывают прерванное чтение диапазона с частичными байтами, S3 RequestTimeout/HTTP client timeout, изменение ETag между частями, отсутствие открытого GET при медленном UploadPart, retry проверки существующих копий без двойного учёта и отсутствие raw SDK сообщения/credentials в диагностике. Точная причина прежнего production-сбоя файла 22 ГБ неизвестна: доступного лога нет; тестами подтверждён риск удержания соединения источника между загрузками частей и его устранение, а не воспроизведение десятичасового канала провайдера.
