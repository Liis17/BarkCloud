# Плейсхолдеры превью из девяти цветов

Parent: [[modules/backend-files]] · Web: [[modules/backend-web]] · API: [[api/files-api]] · Upload: [[modules/upload-2]] · Contracts: [[modules/shared-proto]]

## Расчёт и хранение

`Domain/FilePlaceholder.cs` и таблица `FilePlaceholders` хранят `FileId` (PK/FK оригинала), `Colors` (PostgreSQL `text[]`, ровно 9 строк `#RRGGBB`), `AspectRatio` и `SourceFilePreviewId` (FK **связки** `FilePreviews`). Миграция — `20261002233104_AddFilePlaceholders`. Удаление оригинала либо использованной связки каскадно удаляет цвета; перенос записи каталога в корзину их сохраняет.

`ImagePlaceholderSampler.SampleAsync` декодирует превью через ImageSharp с EXIF-ориентацией. У фото берёт центральный квадрат `min(width,height)`, у видео — всю готовую обложку. Точки находятся в центрах сетки 3×3: `1/6`, `1/2`, `5/6` по обеим осям. Цвет каждой точки — среднее RGB ограниченной областью зоны 5×5; каналы округляются до целого. Порядок — слева направо, сверху вниз. Пропорции относятся к обработанной области, поэтому у фото это `1`, у широкого видео обычно `16/9`.

`FilePlaceholderService.EnsureAsync` выбирает самое маленькое обычное превью (128 → 512 → 1024), а для фото без него — JpegView (`TargetWidth=0`). Новые загрузки используют уже сгенерированные JPEG-байты, привязанные к ID конкретного сохранённого превью-блоба; если другой пайплайн заменил источник, старые байты отбрасываются. Бэкафилл читает только превью через его собственный S3-профиль. Оригинал ради цветов не скачивается. Сохранение выполняется условным `INSERT ... ON CONFLICT`: воркер вставляет только отсутствующие записи, пайплайн может заменить запись при смене источника. Перед вставкой повторно проверяются существование оригинала и актуальная предпочтительная связка, поэтому старый результат после удаления/замены обложки отбрасывается.

## Пайплайн и фон

`PreviewPersistenceService.PersistPreviewsAsync` рассчитывает цвета после сохранения связок. Его `EnsurePlaceholderAsync` также вызывается общим `UploadFile`-хэндлером для JpegView и `LegacyJpegViewBackfillService`. Legacy-обработка превью и ручная смена обложки видео проходят через тот же сервис. Upload 2.0 завершает эту обработку до `ready`. Ошибка цветов логируется и не делает загрузку неуспешной; отмена операции распространяется дальше.

`PersistJpegViewAsync` возвращает `(FileId, SavedBytes)`: байты подтверждаются только после создания блоба или дедупликации по SHA-256. Если связка уже существовала, `SavedBytes=null`: при необходимости цвета читаются из сохранённого превью, а свежесгенерированные байты не приписываются старому ID.

`FilePlaceholderBackfillService` — отдельный `BackgroundService`: первый проход через 60 секунд после запуска, далее через 5 минут после окончания предыдущего. Готовые облачные фото/видео без цветов выбираются порциями по 200 с курсором `FileId`, по одному файлу с отдельным DI scope. Аватары, служебные превью и processing-файлы исключены. Нет источника или ошибка файла — остальные продолжают обрабатываться; пропущенное повторно проверяется в следующем проходе. В .NET 10 весь `ExecuteAsync` выполняется в фоне ([Microsoft](https://learn.microsoft.com/en-us/dotnet/core/compatibility/extensions/10.0/backgroundservice-executeasync-task)).

## API и веб

`FilePlaceholderInfo { repeated string colors=1; float aspect_ratio=2; }` передаётся в `UploadFileInfo.placeholder=19` и `SearchHit.placeholder=15`. Галереи `ListUserMedia`, динамические папки (включая дубликаты), `SearchFiles`, единый `SearchApi`/`ResolveHit`, `GetFileData` и `GetFilesData` подтягивают цвета пакетно на страницу. Web JSON содержит `placeholder: { colors, aspectRatio }`; отдельного browser-запроса нет. Маленькие фото используют `jpegViewUrl`, а единый поиск отдаёт URL JpegView в `previewUrl`. iOS-копию и Swift-стабы синхронизирует существующий `Ios/BarkCloud/sync_proto.sh`; мобильный UI не меняется.

`MediaThumb` включает новый режим через `colorPlaceholder` на страницах «Фото», «Видео» (включая featured), в сетке динамических папок и на странице поиска (сетка и список для фото/видео). Контекстный поиск галерей также использует режим. Другие экраны и полноэкранный просмотр сохраняют прежнее поведение.

Inline SVG состоит из непрозрачного чёрного фона и 9 кругов с alpha `0.9`, радиусом `35%` меньшей стороны и общим Gaussian blur `12%` меньшей стороны, со смешиванием в sRGB. SVG использует переданные пропорции и центральный `cover`. При некорректных цветах остаётся обычная иконка-плейсхолдер. Размеры карточек, `srcset`, `sizes` и lazy loading сохраняются.

Изображение скрыто под плейсхолдером до успешного `img.decode()` ([HTML Standard](https://html.spec.whatwg.org/multipage/embedded-content.html#dom-img-decode)). Одним React-обновлением изображение показывается, а SVG с фильтром размонтируется; перехода прозрачности и постоянного графического кэша нет. Смена источника создаёт новый цикл загрузки, завершение старого запроса игнорируется. Ошибка сети/декодирования сохраняет плейсхолдер и скрывает сломанное изображение.

## Проверки и внедрение

Проверки расчёта: `ImagePlaceholderSamplerTests`; хранения/пайплайна: `FilePlaceholderServiceTests`; реального PostgreSQL, гонок, каскадов и воркера: `FilePlaceholderPostgresTests`. Для PostgreSQL нужен `BARKCLOUD_TEST_POSTGRES` (изолированные базы создаются и удаляются хелпером тестов). Передачу данных проверяют `FilePlaceholderApiTests`, тесты существующих хэндлеров, `UnifiedSearch*Tests` и `CloudJsonTests`. Состояния браузера — `MediaThumb.test.tsx`; прогрессивный JPEG и удаление SVG дополнительно проверяются в браузере.

Внедрение: **миграция и Files → Web**. Пока старые файлы обрабатываются либо источник ещё не создан, клиент использует текущий плейсхолдер. Цвета существующих файлов появляются автоматически в фоновых проходах.

Проверено 2026-10-03: полный Files-набор — 548 тестов без пропусков (включая PostgreSQL), полный Web-набор, 100 frontend-тестов, TypeScript и production-сборки Files/Web/SPA. Модель EF соответствует миграции. В браузере проверены частичная загрузка прогрессивного JPEG, кэш, смена источника, ошибки и миниатюры поиска 44×44: до готовности виден SVG, после декодирования его нет в DOM. Ревью правил проекта и соответствия плану завершилось без оставшихся замечаний.
