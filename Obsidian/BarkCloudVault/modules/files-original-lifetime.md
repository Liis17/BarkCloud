# Жизнь оригинала и облачные ссылки (F15)

Parent: [[modules/backend-files]] · See also: [[modules/backend-files-cloud]] · [[modules/upload-2]] · [[structure/testing]]

## Инвариант

Успешный Attach создаёт ссылку на существующий ready-оригинал, которым владеет вызывающий пользователь. Purge не освобождает пару `(OwnerId, FileId)`, пока у неё есть хотя бы одна запись облака, включая корзину. Общий оригинал удаляется только после освобождения всех владельцев и отсутствия любых `CloudFileEntry`.

## Общая граница БД

`ICloudHierarchyStorage.LockTree(ownerId)` открывает транзакцию и вызывает внутренний `FilesContext.LockCloudTreesAsync`. Ключ PostgreSQL сохранён: `pg_advisory_xact_lock(hashtextextended('cloud-tree:{ownerId}', 0))`. Хелпер требует уже открытую транзакцию; на SQLite advisory-замков нет.

- Attach занимает дерево **до** `GetFile`/проверок владельца и ready и держит его до сохранения ссылки и commit. `GetFile` использует `AsNoTracking` и читает актуальные данные после ожидания.
- `DeleteUserMedia` использует ту же границу до чтения оригинала, изменения живой записи или создания записи корзины. Лог и активность записываются после commit.
- Restore использует тот же замок: восстановление первым сохраняет оригинал; purge первым оставляет restore доменный `FileEntryNotFound`.
- `TrashPurgeService.PurgeCoreAsync` сначала берёт все деревья из входного набора, затем перечитывает кандидатов из БД. Условный gate сохраняет `IsDeleted` и для воркера `PurgeAt <= cutoff`. Результат вычисляется по реально удалённым актуальным кандидатам, а не по отсутствующим строкам старого снимка.
- Удаление записей, `stillReferenced`, очистка зависимостей, освобождение владельцев оригиналов и превью выполняются в одной DB-транзакции. Общая граница используется ручным purge и `TrashCleanupService`.

Порядок блокировок: уникальные `OwnerId` по возрастанию → UPDATE оригиналов по `FileId`, затем `OwnerId` → строки превью по `Id` через существующий `LockLiveFilesAsync`. Все замки владельцев берутся до блокировок строк; вложенных транзакций нет. Батчи могут содержать разных владельцев общих оригиналов и общие превью.

## Orphan cleanup и отказ S3

Физическая очистка выполняется **после освобождения tree locks**. Каждый блоб занимает отдельная транзакция: условный DELETE `UploadedFiles` при пустом `Uploaders` **и отсутствии любых CloudFileEntry** → S3 Delete → удаление хеша и связок превью → commit.

Ошибка S3 откатывает захват строки, хеш и связки остаются для повторной попытки `OrphanBlobCleanupService`. Владельцы, освобождённые предыдущей DB-фазой purge, при этом не возвращаются; Attach такого оригинала получает `CloudAccessDenied` либо `FileNotFound`.

Атомарные операции `FileOwnership` сохранены. Добавление владельца до захвата orphan-строки предотвращает удаление; после захвата оно ждёт и не воскрешает удалённый оригинал. Дедуп оригиналов отключён; существующая дедупликация превью сохраняет проверку и привязку под блокировкой строки превью.

## FK и миграция

`20261008052536_EnforceCloudFileOriginalIntegrity` добавляет индекс по `CloudFileEntries.FileId` и FK `CloudFileEntry.FileId → UploadedFiles.Id` с `Restrict`. Наличие живой или корзинной записи запрещает удаление оригинала; каскадного удаления облачных записей нет.

Перед добавлением FK миграция в транзакции блокирует `UploadedFiles` и `CloudFileEntries` (`SHARE ROW EXCLUSIVE`) и удаляет только облачные записи без оригинала. Это выбранная политика для существующих повреждённых данных; оригиналы, корректные записи, другие метаданные и S3 не изменяются. `Down` снимает FK/индекс, удалённые записи не восстанавливает.

Внедрение: остановить все Files-реплики и воркеры, сохранить резервную копию БД, запустить одну новую реплику для миграции, затем остальные. `Program` применяет миграции до обработки RPC и старта фоновых служб.
