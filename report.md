В backend обнаружены проблемы разграничения доступа, восстановления аккаунта, согласованности данных и обработки отказов. ## Область и метод проверки

Проверены основные пути в `Configuration`, `Identity`, `Users`, `Files`, `Notification`, `Torrent`, серверной части `Web`, общей библиотеке `GrpcServer` и `Shared`: аутентификация и отзыв токенов, загрузка/скачивание, владение файлами, корзина, дерево папок, поиск, обработчики очередей, управление торрентами, настройки и CI. Использованы исходники, EF-модели и миграции, конфигурация запуска, тесты и диагностические сообщения сборки. Это обзор архитектуры и целевых участков кода, а не утверждение о ручной проверке каждой строки backend.

Отчёт относится к состоянию рабочего дерева на момент проверки. Во время аудита параллельно менялись `UnifiedSearchService.cs` и его тесты. После этих изменений тесты Files были запущены повторно и прошли; промежуточные три ошибки поиска не включены в список открытых дефектов. Production-код в рамках этого аудита не исправлялся.

Находки F01–F24 подтверждены статическим анализом конкретных участков. Приведённые сценарии объясняют возможное следствие кода; эксплуатация на работающем сервере и конкурентные сценарии динамически не воспроизводились. Q01–Q02 дополнительно подтверждены сборкой/NuGet, Q03 — оценка сопровождаемости. Нагрузочные показатели, фактические настройки развёрнутого сервера и внешние ограничения трафика не измерялись.

Приоритеты:

- **P1** — исправить в первую очередь: нарушение доступа, риск потери данных/аккаунта или серьёзный сбой основного сценария.
- **P2** — исправить следующим этапом: отказоустойчивость, масштабирование, условные функциональные дефекты и недостатки проверок.
- **P3** — технический долг, который повышает стоимость и риск последующих изменений.

## Проблемы с приоритетом P1

### F01. Выдача ссылки на чужой приватный оригинал

**Код:** [FilesApiService.cs:121](Backend/BarkCloud.Files/Host/FilesApiService.cs#L121), [GetTempDownloadUrlCommandHandler.cs:36](Backend/BarkCloud.Files/Features/GetTempDownloadUrl/GetTempDownloadUrlCommandHandler.cs#L36), [UploadedFilesStorage.cs:54](Backend/BarkCloud.Files/Persistence/UploadedFilesStorage.cs#L54).

`FilesApi` требует пользовательский JWT, но `GetTempDownloadUrl` передаёт только список GUID. Storage выбирает готовые файлы по ID, а handler создаёт `TempFile` без проверки текущего пользователя, живой записи в его облаке или разрешения на доступ. Общая аутентификация не проверяет владение конкретным файлом.

**Сценарий и последствия:** пользователь A, узнав ID приватного файла B, запрашивает временную ссылку и скачивает оригинал. Перебор случайных UUID не предполагается: необходим известный идентификатор. Аналогичный недостаток проверки владельца есть в старых обработчиках [GetFileData](Backend/BarkCloud.Files/Features/GetFileData/GetFileDataCommandHandler.cs#L37) и [GetFilesData](Backend/BarkCloud.Files/Features/GetFilesData/GetFilesDataCommandHandler.cs#L35), которые выдают данные по ID.

**Исправление:** перед выдачей данных и временных ссылок применять общую проверку доступа: владелец либо явно действующий grant/share с подходящими правами. Учитывать состояние удаления и отзыва разрешения.

**Проверка:** два пользователя, приватный файл B: запрос A отклоняется и не создаёт `TempFile`; владелец и получатель действующего разрешения скачивают файл; после отзыва разрешения новая ссылка не выдаётся.

### F02. Сброс пароля не изолирован от прежних сессий

**Код:** [ConfirmResetPasswordCommandHandler.cs:154](Backend/BarkCloud.Identity/Features/ConfirmResetPassword/ConfirmResetPasswordCommandHandler.cs#L154), [SetPasswordCommandHandler.cs:58](Backend/BarkCloud.Identity/Features/SetPassword/SetPasswordCommandHandler.cs#L58), [CreateTokenCommandHandler.cs:19](Backend/BarkCloud.Identity/Features/CreateToken/CreateTokenCommandHandler.cs#L19).

Подтверждение сброса выдаёт обычные access/refresh-токены, помечает reset использованным и очищает общий хеш пароля. Прежние refresh-токены не удаляются. `SetPassword` требует старый пароль только при ненулевом хеше; у любого ещё действующего пользовательского JWT появляется возможность установить пароль в промежутке до завершения восстановления. Refresh проверяется без версии учётных данных или признака сброса.

**Сценарий и последствия:** у злоумышленника сохранилась прежняя сессия. Владелец подтверждает восстановление; прежняя сессия может первой вызвать `SetPassword` без старого пароля. Даже после установки пароля ранее выданный refresh продолжает работать. Восстановление не гарантирует возвращение контроля над аккаунтом.

**Исправление:** использовать отдельное ограниченное разрешение на восстановление, атомарно устанавливать новый хеш и отзывать прежние сессии. Отсутствие общего хеша не должно давать обычной сессии дополнительное право. Однократное использование reset тоже фиксировать атомарно с результатом операции.

**Проверка:** после восстановления прежние access/refresh отклоняются; новый пароль может установить только разрешение данного reset; два параллельных подтверждения одного reset дают один успешный результат.

### F03. SMTP принимает любой TLS-сертификат

**Код:** [EmailSender.cs:37](Backend/BarkCloud.Notification/Senders/EmailSender.cs#L37).

Перед отправкой письма устанавливается глобальный `ServicePointManager.ServerCertificateValidationCallback = (...) => true`. `EnableSsl = true` шифрует канал, но проверка подлинности SMTP-сервера отключена. Использование этого callback в `SmtpClient` подтверждается [исходником .NET 10](https://raw.githubusercontent.com/dotnet/runtime/v10.0.0/src/libraries/System.Net.Mail/src/System/Net/Mail/SmtpConnection.cs).

**Последствия:** при возможности подменить сетевой путь/SMTP-сервер можно перехватить SMTP-учётные данные и письма с кодами входа и восстановления. Это условие атаки, а не утверждение о выполненной MITM-проверке. Влияние на все другие HTTP-клиенты здесь не заявляется.

**Исправление:** удалить разрешающий callback, использовать штатную проверку сертификата и корректную цепочку доверия для SMTP.

**Проверка:** доверенный SMTP работает; сервер с недоверенным сертификатом или неверным hostname вызывает TLS-ошибку до передачи учётных данных.

**Статус (2026-10-02): исправлено в коде.** Отправка переведена на MailKit 4.18.1: TLS и штатная проверка сертификата включены по умолчанию; 465 — implicit TLS, остальные порты — обязательный STARTTLS. `SMTP_ALLOW_INSECURE=true`, явно заданный оператором в окружении контейнера Notification, отключает проверку только данного SMTP-клиента и допускает plaintext при отсутствии STARTTLS. Ошибка начатого TLS не вызывает переход на plaintext. Флаг по умолчанию `false`, некорректное значение останавливает запуск, небезопасный режим отмечается warning. Локальный SMTP/TLS-стенд подтвердил отказ до AUTH/письма для недоверенного/просроченного сертификата, неверного hostname и отсутствия TLS, а также работу обоих режимов, доверенного тестового CA и implicit TLS. Проверка из production Docker-образа пока не выполнена: Docker runtime отсутствует в среде реализации.

### F04. Username/email не защищены уникальными ограничениями

**Код:** [ChangeUsernameCommandHandler.cs:32](Backend/BarkCloud.Users/Features/ChangeUsername/ChangeUsernameCommandHandler.cs#L32), [UsersStorage.cs:126](Backend/BarkCloud.Users/Persistence/Services/UsersStorage.cs#L126), [AddUserLookupIndexes.cs:17](Backend/BarkCloud.Users/Persistence/Migrations/20260602120000_AddUserLookupIndexes.cs#L17).

Изменение username проверяет зарезервированные имена, но не занятость другим пользователем. Storage безусловно сохраняет новое значение. Индексы `lower(Username)` и `lower(Email)` не уникальные; отдельного ограничения уникальности в модели/миграциях не найдено. Поиск при входе использует `FirstOrDefault`.

**Сценарий и последствия:** B меняет имя на существующее имя A. Запросы профиля и входа становятся неоднозначными: выбор одной из строк не соответствует ожидаемой идентичности. Предварительные проверки регистрации также не предотвращают одновременное создание одинаковых логинов.

**Исправление:** ввести уникальные ограничения для нормализованных username и непустых email согласно правилам проекта; проверять занятость при переименовании и корректно преобразовывать конфликт БД в доменную ошибку. Перед миграцией отдельно разрешить существующие дубли.

**Проверка:** занятое имя, варианты регистра букв и конкурентная регистрация не создают дублей; допустимая смена имени и режим без email продолжают работать.

### F05. Регистрация ограничена одним ID в секунду

**Код:** [UsersStorage.cs:51](Backend/BarkCloud.Users/Persistence/Services/UsersStorage.cs#L51).

`CreateUser` присваивает первичному ключу `DateTimeOffset.UtcNow.ToUnixTimeSeconds()`. Два создания пользователя за одну секунду получают одинаковый ID. Явно заданное ненулевое значение сохраняется как ключ, а не заменяется автоматически sequence.

**Последствия:** даже пользователи с разными логинами конфликтуют по primary key. Параллельная регистрация или создание draft-пользователей возвращает ошибку БД. Проблема возникает при небольшой активности.

**Исправление:** получать `long` ID из PostgreSQL identity/sequence с корректной стартовой величиной выше существующих ключей. Время регистрации хранить в отдельном поле, которое уже есть.

**Проверка:** серия из 200 конкурентных регистраций с разными именами в реальном PostgreSQL создаёт 200 пользователей с различными ID.

### F06. Фоновая очистка может удалить восстановленный файл

**Код:** [TrashCleanupService.cs:63](Backend/BarkCloud.Files/Services/TrashCleanupService.cs#L63), [TrashPurgeService.cs:88](Backend/BarkCloud.Files/Services/TrashPurgeService.cs#L88), [RestoreFromTrashCommandHandler.cs:67](Backend/BarkCloud.Files/Features/Cloud/RestoreFromTrash/RestoreFromTrashCommandHandler.cs#L67).

Воркер сначала выбирает просроченные записи корзины, затем удаляет их по ID. На этапе `ExecuteDeleteAsync` условие `IsDeleted`/`PurgeAt` повторно не проверяется. Восстановление независимо сбрасывает признаки удаления. После удаления записи purge снимает владельца с блоба и может удалить оригинал из S3.

**Сценарий и последствия:** воркер выбрал запись → пользователь успешно восстановил файл → воркер удалил выбранный ID. При отсутствии других ссылок теряется и физический оригинал. Успешный ответ восстановления не гарантирует сохранность данных.

**Исправление:** атомарно переводить подходящие записи в состояние окончательного удаления; восстановление и purge должны согласованно проверять это состояние. Удалять только реально захваченные для purge строки. Длительное удаление из S3 выполнять через возобновляемую процедуру после короткой транзакции БД.

**Проверка:** тест с барьерами между выборкой, восстановлением и purge: восстановленный файл и его S3-объект остаются доступны либо восстановление заранее получает явный отказ.

### F07. Email-код входа многоразовый и не имеет срока жизни

**Код:** [AuthUserProperty.cs:20](Backend/BarkCloud.Identity/Domain/AuthUserProperty.cs#L20), [AuthPropertiesStorage.cs:122](Backend/BarkCloud.Identity/Persistence/Services/AuthPropertiesStorage.cs#L122), [AuthCommandHandler.cs:99](Backend/BarkCloud.Identity/Features/Auth/AuthCommandHandler.cs#L99), [AuthCommandHandler.cs:177](Backend/BarkCloud.Identity/Features/Auth/AuthCommandHandler.cs#L177).

Email-2FA входа хранит один `LastEmailAuthCode`. Проверка сравнивает строку без срока действия, числа попыток и атомарного расходования. Успешный вход код не очищает. Кроме того, выдача нового кода и отправка письма происходят до проверки пароля, которая находится ниже, на строке 202.

**Последствия:** ранее полученный код можно использовать повторно с правильным паролем, пока его не заменили. Зная логин, можно отправлять письма и заменять код текущего входа без знания пароля. Вывод относится к `LastEmailAuthCode`, а не ко всем механизмам OTP: у запросов восстановления отдельный срок действия есть.

**Исправление:** проверять пароль перед выдачей challenge; хранить назначение, срок, лимит попыток и использованность кода; успешную проверку расходовать атомарно. Ограничить повторную отправку.

**Проверка:** просроченный и повторно использованный код отклоняются; неверный пароль не отправляет письмо и не заменяет код; параллельное использование одного challenge успешно только один раз.

### F08. Изменение 2FA не защищает действующую настройку

**Код:** [EnableOtpVerificationCommandHandler.cs:92](Backend/BarkCloud.Identity/Features/EnableOtpVerification/EnableOtpVerificationCommandHandler.cs#L92), [AuthPropertiesStorage.cs:25](Backend/BarkCloud.Identity/Persistence/Services/AuthPropertiesStorage.cs#L25), [DisableOtpVerificationCommandHandler.cs:103](Backend/BarkCloud.Identity/Features/DisableOtpVerification/DisableOtpVerificationCommandHandler.cs#L103).

Повторное включение Authenticator генерирует и сразу записывает новый `OtpSecret`, даже когда `OtpEnabled` уже равен `true`. Действующий секрет заменяется до подтверждения нового. Проверка действующего второго фактора для этой смены отсутствует. Отключение email-2FA также не проверяет код или пароль; наличие пользовательской сессии считается достаточным.

**Сценарий и последствия:** пользователь повторно открыл настройку и закрыл QR-экран — прежний Authenticator уже перестал подходить. Обладатель похищенной сессии может заменить секрет или отключить email-2FA без повторного подтверждения владельца.

**Исправление:** хранить ожидающий подтверждения секрет отдельно; переключать активный секрет только после проверки нового кода и недавнего подтверждения владельца. Для смены/отключения действующего 2FA требовать повторную аутентификацию.

**Проверка:** повторное открытие и отмена настройки не меняют активный секрет; без подтверждения прежнего способа смена/отключение отклоняются.

### F09. Torrent и локальная авторизация Web не учитывают отзыв сессии

**Код:** [Torrent/Program.cs:62](Backend/BarkCloud.Torrent/Program.cs#L62), [TorrentController.cs:16](Backend/BarkCloud.Torrent/Host/TorrentController.cs#L16), [AuthGateway.cs:70](Backend/BarkCloud.Web/Auth/AuthGateway.cs#L70), [AuthGateway.cs:218](Backend/BarkCloud.Web/Auth/AuthGateway.cs#L218).

Torrent подключает общий JWT-auth, но не регистрирует consumer события `SessionRevokedEvent`, который подключён в Identity/Users/Files. Его локальный кэш отзыва не получает события. Web принимает cookie с JWT после локальной проверки подписи, issuer/audience, типа и срока; проверку отзыва не выполняет.

**Последствия:** сохранённая копия access-токена после logout/удаления сессии продолжает открывать Torrent API/скачивание до истечения JWT. **Частично закрыто F10 (2026-10-02):** Identity больше не публикует события отзыва: refresh-delete + `RevokedSession` сохраняются атомарно, повторная доставка удаления пользователя безопасна для отзыва. Риск потери `UserDeleted` после коммита Users сохраняется и требует отдельного решения F11.

**Исправление:** сохранять изменения и исходящие события в одной транзакции соответствующей БД; применять transactional outbox и идемпотентную обработку. Данные для последующей рассылки отзывов должны переживать повторную доставку.

**Проверка:** отказ публикации непосредственно после изменения БД, затем восстановление RabbitMQ/рестарт: все события доставлены, связанные данные удалены, старые сессии отозваны; повторная доставка безопасна.

### F16. Корневые папки обходят уникальность имени

**Код:** [FilesContext.cs:113](Backend/BarkCloud.Files/Persistence/FilesContext.cs#L113), [CreateDirectoryCommandHandler.cs:49](Backend/BarkCloud.Files/Features/Cloud/CreateDirectory/CreateDirectoryCommandHandler.cs#L49), [AddCloudDirectories.cs:51](Backend/BarkCloud.Files/Persistence/Migrations/20260518174041_AddCloudDirectories.cs#L51).

Unique-индекс задан по `(OwnerId, ParentId, Name)`, но `ParentId` у корневых папок равен `NULL`. PostgreSQL по умолчанию считает NULL различными в таком индексе, поэтому он разрешает одинаковые корневые имена. Это следует из [документации PostgreSQL](https://www.postgresql.org/docs/current/indexes-unique.html). Предварительная проверка имени и INSERT не атомарны. Индекс системных папок по `(OwnerId, SystemKind)` тоже не уникальный.

**Последствия:** параллельное создание одинаковых папок в корне может успешно создать две строки; аналогичная гонка возможна при обеспечении существования системной папки. Последующие разрешения имени/типа становятся неоднозначными.

**Исправление:** отдельный partial unique-индекс для `ParentId IS NULL` либо `NULLS NOT DISTINCT` при поддержке используемой версии PostgreSQL; уникальность системных папок закрепить отдельно. Перед миграцией убрать дубли, конфликт INSERT преобразовывать в ожидаемую ошибку.

**Проверка:** реальный PostgreSQL, два одновременных создания корневой/системной папки: сохраняется одна строка. SQLite-тест не подтверждает семантику производственной БД.

**Статус F16 — исправлено (2026-10-02):** имена корневых папок защищены partial unique-индексом `(OwnerId, Name) WHERE ParentId IS NULL`; прежний индекс вложенных имён сохранён. Индекс `(OwnerId, SystemKind) WHERE SystemKind <> 0` стал unique независимо от имени/родителя. `AddDirectory`/`UpdateDirectory` возвращают прежний `DirectoryNameConflict` только для `23505` индексов имён; устаревшее переименование/перемещение больше не перезаписывает системный тип. `EnsureSystemDirectory` после конфликтов возвращает ID победителя, обычную корневую папку повышает условно (во внешней транзакции — savepoint), чужой системный тип сохраняет и использует суффикс; неуспешная Added-сущность отсоединяется, другие ошибки не повторяются. ### F23. Unicode в секрете JWT ломает проверку токенов

**Статус F23 — исправлено (2026-10-02):** единственный способ получить байты ключа — `JwtSecret.GetKeyBytes` (`Shared.Identity`): UTF-8, для ASCII-секретов байты прежние. При не-ASCII секрете сохранённые `*Service:Token` (подписаны по ASCII-ключу) перестанут проходить проверку: очистить их в Configuration и перезапустить Configuration (`PopulateDefaultsAsync` выпустит новые), все сервисы обновлять одним релизом. Секрет короче 16 байт после обновления остановит сервисы с понятной ошибкой — значение исправить прямо в БД Configuration. Вне объёма: смена секрета через UI не перевыпускает сохранённые сервисные токены. Проверено: новые тесты `JwtSecret`, `AddXAuth`, кросс-тест Identity → `AddXAuth` (на ASCII-проверке с кириллическим секретом падает, после правки проходит), `AuthGateway`, `AdminGate`, `ServiceToken`, валидатор и populator Configuration; тесты Configuration, GrpcServer, Identity, Notification, Torrent, Users, Web проходят (Files.Tests и PostgreSQL-интеграционные в среде не запускались), Docker-прогон не выполнялся. **Код:** [JwtService.cs:50](Backend/BarkCloud.Identity/Services/JwtService.cs#L50), [XAuthExtensions.cs:28](Backend/BarkCloud.GrpcServer/XAuth/XAuthExtensions.cs#L28), [AuthGateway.cs:58](Backend/BarkCloud.Web/Auth/AuthGateway.cs#L58), [SettingsValueValidator.cs:13](Backend/BarkCloud.Configuration/Catalog/SettingsValueValidator.cs#L13).

**Последствия:** конфигурация с достаточно длинным секретом, содержащим кириллицу/другой Unicode, принимается, но выпущенные Identity токены не проходят подпись в остальных сервисах. При ASCII-секрете этот дефект не проявляется.

**Исправление:** единое преобразование секрета в байты во всех сервисах и проверка пригодности ключа при настройке/старте. При изменении формата предусмотреть согласованное обновление сервисов.

**Проверка:** одним ASCII- и одним не-ASCII-секретом подписать и проверить пользовательский/сервисный токен всеми потребителями; короткий/недопустимый ключ даёт понятную ошибку конфигурации.

Здесь существеннее смешение маршрутизации, преобразования DTO, внешних вызовов и обработки ошибок, а также параллельные реализации выпуска сессии в `AuthCommandHandler` и `SessionIssuer`. **Рекомендация:** после функциональных исправлений локально выделять группы endpoint по существующим областям и переиспользовать общий сценарий выпуска сессии. **Проверка:** поведение API и тесты остаются прежними; один общий сценарий проверяет реакцию всех способов входа на сбои уведомлений; отмена клиента прекращает соответствующую работу.

## Что уже реализовано корректно

Старый [SECURITY_AUDIT_FINDINGS.md](Docs/audit/SECURITY_AUDIT_FINDINGS.md) полезен как история, но его статусы требуют сверки с текущим кодом. Проверены следующие изменения:

- **Configuration защищён при production-запуске:** [Program.cs:19](Backend/BarkCloud.Configuration/Program.cs#L19) требует настроенный access key вне Development; серверный interceptor проверяет ключ. Прежнее утверждение о полностью открытом Configuration нельзя переносить на текущую версию.
- **Резервирование квоты есть:** [StorageQuotaService.cs:23](Backend/BarkCloud.Files/Services/StorageQuotaService.cs#L23) использует PostgreSQL advisory lock, а UploadSessionCoordinator/LegacyUploadQuotaGuard выполняют резервирование в транзакции. Это не исправляет раннюю буферизацию HTTP-тела из F12.
- **Files использует EF bus outbox:** [Program.cs:128](Backend/BarkCloud.Files/Program.cs#L128); перевод upload session в processing и публикация объединены в транзакции [UploadSessionCoordinator.cs:610](Backend/BarkCloud.Files/Services/UploadSessionCoordinator.cs#L610). В F11 речь о других сервисах/путях.
- **Таймауты FFmpeg/FFProbe присутствуют:** [VideoThumbnailExtractor.cs:26](Backend/BarkCloud.Files/Services/VideoThumbnailExtractor.cs#L26) задаёт 2 минуты для probe и 15 минут для FFmpeg с cancellation. Прежний пункт «FFmpeg без таймаута» не соответствует этому коду.
- **Проверка размера изображения выполняется до декодирования:** [ImageCompressor.cs](Backend/BarkCloud.Files/Services/ImageCompressor.cs) вызывает предварительную проверку количества пикселей.
- **Скачивание использует поток/Range:** [DownloadFileCommandHandler.cs](Backend/BarkCloud.Files/Features/DownloadFile/DownloadFileCommandHandler.cs) работает с потоком S3; утверждение о загрузке каждого оригинала целиком в RAM для этого пути не подтвердилось.
- **Проверка хеша учитывает пользователя:** [CheckFileHashCommandHandler.cs](Backend/BarkCloud.Files/Features/CheckFileHash/CheckFileHashCommandHandler.cs) проверяет доступность файла для владельца; это отличается от небезопасной выдачи временных URL в F01.
- **SMTP защищён по умолчанию (F03, 2026-10-02):** MailKit требует TLS и проверяет сертификат; небезопасный режим включается оператором только через `SMTP_ALLOW_INSECURE=true`. Локальные SMTP/TLS-тесты прошли; проверка из production Docker-образа остаётся для развёртывания.

## Рекомендуемый порядок исправлений

1. **Доступ и контроль аккаунта:** F01–F03, F07–F10, F14. Критерий: нельзя получить приватный оригинал другого пользователя; восстановление исключает прежние сессии; 2FA безопасно меняется; отзыв действует после рестарта и на всех точках входа; SMTP проверяет сертификат; попытки ограничиваются.
2. **Целостность данных и регистрация:** F04–F06, F11–F13, F15–F16. Критерий: конкурентные регистрации/переименования/перемещения сохраняют инварианты; восстановленный файл не удаляется; события переживают отказ очереди; временный диск имеет ограниченный бюджет.
3. **Отказы и пропускная способность:** F17–F22. Критерий: медленные загрузки и отмена управляются явно; ошибочные задачи не блокируют здоровые; уведомления не искажают результат; поиск ограничивает объём работы; состояние и статистика торрентов восстанавливаются после ошибки.
4. **Конфигурация, CI и сопровождение:** F23–F24, Q01–Q03. Критерий: общий контракт JWT, полные dependency filters, тесты Torrent в CI, отсутствие конфликтов protobuf/advisory, сокращение доказанного дублирования.

Для первых двух этапов нужны интеграционные проверки с реальным PostgreSQL и контролируемыми отказами RabbitMQ/S3. Конкурентные тесты следует синхронизировать барьерами на проверенных границах операций; случайный `Task.WhenAll` без управления порядком не гарантирует воспроизведение гонки. Сценарии проверки для каждой находки выше являются критериями приёмки будущих исправлений.
