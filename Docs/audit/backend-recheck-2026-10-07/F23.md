# F23 — startup принимает непригодный HS256-ключ

Срез: `d6563a2`, повторная проверка 2026-10-07. **Статус: актуален. Приоритет: P2.** Production-код при проверке не менялся.

## Причина и влияние

[JwtSecret.cs:15](/Users/liis/Projects/BarkCloud/Shared/BarkCloud.Shared.Identity/JwtSecret.cs:15) устанавливает `MinStartupBytes = 16`; [GetKeyBytes](/Users/liis/Projects/BarkCloud/Shared/BarkCloud.Shared.Identity/JwtSecret.cs:24) использует этот минимум по умолчанию. [AddXAuth](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.GrpcServer/XAuth/XAuthExtensions.cs:20) строит ключ при регистрации аутентификации, поэтому 16–31 UTF-8 байт проходят эту раннюю проверку.

Однако [JwtService.cs:50](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Identity/Services/JwtService.cs:50) передаёт эти байты настоящему `SigningCredentials(..., HmacSha256)`, и установленный signer отклоняет такой ключ при [CreateToken](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Identity/Services/JwtService.cs:63) с `IDX10720`.

Следствие: конфигурация допускается ранней проверкой, но login, refresh или выпуск служебных токенов падают при подписании. Это несогласованность обязательного минимума и реального signer; не доказанная возможность подделки JWT.

[SettingsValueValidator](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Configuration/Catalog/SettingsValueValidator.cs:16) уже требует 32 байта при сохранении нового значения. Это не исправляет ранее сохранённые значения и другие источники конфигурации.

## Динамическое воспроизведение

Отдельный [harness](evidence/identity/Program.cs) вызвал настоящий `JwtSecret.GetKeyBytes`, затем `JwtService.GenerateUserToken`. Для допустимого ключа выполнялась настоящая валидация `JwtSecurityTokenHandler.ValidateToken`.

| Длина искусственного ASCII-ключа | Ранняя проверка | Выпуск/валидация JWT |
|---|---|---|
| 15 байт | Отклонён | `InvalidOperationException` helper |
| 16 байт | Принят | `ArgumentOutOfRangeException`, `IDX10720` |
| 31 байт | Принят | `ArgumentOutOfRangeException`, `IDX10720` |
| 32 байта | Принят | Подпись и валидация успешны |

Фактический вывод: [results.txt](evidence/identity/results.txt). Полный запуск приложения не выполнялся; соответствие startup подтверждено статически общим вызовом helper в `AddXAuth`. Signer и validator проверены динамически.

## Задание агенту

Подними общий обязательный startup минимум HS256 до **32 UTF-8 байт**. Исправь комментарий о 128 битах и существующие tests, закрепляющие допустимость 16/20 байт. Добавь граничные tests через настоящий выпуск и валидацию JWT. Сохрани один UTF-8 путь преобразования секрета у всех подписывающих и проверяющих потребителей. Обнови соответствующие заметки Obsidian Vault.

Scope: `JwtSecret`, непосредственно связанные tests и документация. Не требуется менять алгоритм, claims, формат токенов, настройки времени жизни или автоматически ротировать реальные secrets.

## Ловушки

- Считать **байты UTF-8**, а не символы: 16 символов `ж` дают 32 байта, 15 — 30.
- Один тест helper недостаточен: нынешние tests проходят, хотя signer не работает. Проверить `JwtService` и настоящий validator.
- [JwtSecretTests](/Users/liis/Projects/BarkCloud/Tests/Backend/BarkCloud.GrpcServer.Tests/XAuth/JwtSecretTests.cs:43) сейчас ожидает минимум 16; обновить осмысленно, не удалить boundary coverage.
- Сообщения ошибок должны содержать требуемую/фактическую длину, без самого секрета.
- Не делать скрытую замену конфигурации ради прохождения startup. При необходимости смены общего ключа выкладка всех сервисов должна быть согласована; существующие JWT затрагиваются ротацией.
- Общий helper используется также Web и генерацией service tokens: нельзя исправить только один signer, оставив ранние проверки расходящимися.

## Приёмка

1. Null, пустой секрет, 31 ASCII байт и 15 кириллических символов отвергаются ранней проверкой с понятной ошибкой без раскрытия значения.
2. 32 ASCII байта и 16 кириллических символов проходят проверку, подписывают и валидируют JWT.
3. Проверены user/service tokens и единое UTF-8 представление для signer/validator.
4. Граничный тест 31/32 проходит через реальный signer, а не только константу helper.
5. Существующие JWT/auth tests проходят; vault описывает обязательный минимум 32 байта.
