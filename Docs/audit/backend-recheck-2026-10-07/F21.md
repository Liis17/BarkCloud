# F21 · P2 — отказ БД необратимо теряет статистику трафика

Статус на 2026-10-07: **актуален, воспроизведён**. Проверенный срез: `d6563a2`. Код Torrent и его штатные тесты не менялись относительно `575318a`.

## Задание агенту

Исправь подтверждённую потерю `Downloaded`/`Uploaded` в `TorrentPersistenceService`: сессионный baseline должен отражать только успешно сохранённый в БД снимок. Ограничь изменения накоплением статистики и соответствующими регрессионными тестами. Работай в текущей ветке; обнови заметку `Obsidian/BarkCloudVault/modules/backend-torrent.md` после изменения поведения.

## Где и почему ломается

В [TorrentPersistenceService.cs:94](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Torrent/Infrastructure/TorrentPersistenceService.cs:94) воркер снимает `DataBytesReceived`/`DataBytesSent` движка и прибавляет разницу с последним baseline к EF-сущности. В [том же файле:98](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Torrent/Infrastructure/TorrentPersistenceService.cs:98) он сразу меняет `managed.LastSessionDownloaded`/`LastSessionUploaded`, хотя единственный `SaveChangesAsync` для всего списка выполняется позднее — [строка 114](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Torrent/Infrastructure/TorrentPersistenceService.cs:114).

Если сохранение откатилось, EF-контекст уничтожается, БД остаётся прежней, а baseline singleton-движка уже сдвинут. На следующем тике новый контекст читает старые значения БД и считает дельту только от ошибочно сдвинутого baseline. Отброшенная часть больше не учитывается. Аналогичный риск возникает, если после изменения baseline одного торрента падает чтение следующего: до общего сохранения дело вообще не доходит.

## Минимальное воспроизведение

1. БД содержит `Downloaded=100`, `Uploaded=200`; baseline обоих счётчиков равен нулю.
2. Движок накопил `10/20` байт. Flush обновляет baseline до `10/20`.
3. `SaveChangesAsync` завершается ошибкой до commit. В БД по-прежнему `100/200`.
4. Движок получает ещё `5/7` байт. Успешный следующий flush сохраняет `105/207`, хотя должен сохранить `115/227`.

Потеря равна `10/20` байт. Повтор того же flush без нового трафика также не вернёт потерянные значения.

## Влияние

Постоянно занижаются накопленные показатели скачанного/отданного и ratio. Ошибка видна и до рестарта: [TorrentMapper.cs:47](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Torrent/Infrastructure/TorrentMapper.cs:47) строит живой ответ как БД плюс разница относительно этого же baseline. Воркер ловит ошибку и продолжает работу, поэтому последующие успешные тики не сигнализируют о потере.

## Минимальное исправление и ловушки

- Для найденных строк сохранить локальный список `(managed, capturedDown, capturedUp)`; изменять EF-сущности, сохраняя baseline прежним до результата общего `SaveChangesAsync`.
- Только после успешного сохранения установить baseline в **снятые ранее** значения. Не читать монитор повторно после commit: трафик, пришедший во время сохранения, должен попасть в следующий flush.
- При исключении/отмене до commit не менять baseline ни одного элемента этого batch. Не публиковать значения для строки, которую пропустили из-за отсутствия в БД.
- Текущий воркер выполняет flush последовательно. Для этого исправления не нужен глобальный замок движка, удерживаемый во время всех запросов к БД. Если появится несколько писателей статистики, их сериализацию потребуется определить отдельно.
- Не подменять воспроизведение EF InMemory: нужен реальный relational `SaveChanges` с отказом. Не ограничиваться проверкой того, что исключение залогировано.
- Перенос baseline после `SaveChangesAsync` решает подтверждённый откат. Исключение при **неизвестном результате commit** — отдельная ловушка: если commit прошёл, а подтверждение потерялось, слепой повтор инкремента может задвоить дельту. Не объявляй такую доставку exactly-once; при включении этого сценария в гарантию нужен идемпотентный checkpoint/идентификатор сохранённого снимка в БД или проверка результата commit.

## Критерии приёмки

1. Ошибка сохранения до commit оставляет baseline прежним; следующий успешный flush сохраняет всю накопленную дельту ровно один раз.
2. Для примера выше итог БД — `115/227`. Дополнительный flush без нового трафика не меняет итог.
3. Трафик, пришедший во время ожидания commit, сохраняется следующим тиком.
4. Отмена и ошибка чтения позднего элемента batch не сдвигают baseline уже обработанных элементов.
5. Отсутствующая строка не получает новый baseline; успешный batch по нескольким торрентам обновляет только сохранённые снимки.
6. Штатные Torrent-тесты проходят. Обновлена заметка vault с правилом commit → baseline.
