# F17 · P2 — время передачи и отмена legacy upload/import

Проверено 2026-10-07 на `d6563a2160ca8e3b870c32871883aa6fa188b923`. Статус: **актуален**. Этот файл можно целиком передать агенту как задание.

## Проблема и причина

В [Web/Program.cs:89](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Web/Program.cs:89) и [Torrent/Program.cs:66](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Torrent/Program.cs:66) `files-upload` зарегистрирован без настройки `Timeout`. Полученный через фабрику клиент имеет предел 100 секунд на запрос. Медленный или большой допустимый файл может прервать передачу Web → Files или Torrent → Files, хотя Files готов продолжать её. Предел относится к upstream HTTP-запросу, а не ко всему времени загрузки браузером формы в Web. Значение по умолчанию описано в [документации .NET](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.httpclient.timeout?view=net-10.0).

В [CloudApiEndpoints.cs:1317](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Web/Endpoints/CloudApiEndpoints.cs:1317) `PostAsync` не получает `http.RequestAborted`. После отключения браузера Web может продолжать передавать уже принятую форму в Files. В [TorrentImportService.cs:66](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Torrent/Infrastructure/TorrentImportService.cs:66) отмена уже передаётся через `ct`.

Сценарий: upstream-передача продолжается более 100 секунд → клиент отменяет запрос → upload/import возвращает ошибку. Отдельный сценарий: браузер отменяет запрос во время upstream-передачи → передача не получает эту отмену.

## Что исправить

1. Явно установить политику времени передачи для обоих `files-upload`: достаточный согласованный срок либо `InfiniteTimeSpan` с действующей отменой и выбранным ограничением зависшего запроса. Не подбирать произвольный короткий timeout, сохраняющий ту же проблему для больших файлов.
2. Передать `RequestAborted` через операции legacy Web upload: чтение формы, получение upload URL, `PostAsync`, чтение ответа — где API принимает cancellation token.
3. Сохранить отмену Torrent и текущие ошибки/результаты API. Проверить освобождение multipart/потоков при отмене.

Область: две регистрации клиента и legacy-сценарий `/api/files/upload`; Upload 2.0 переделывать не требуется. Клиент Web используется и другими HTTP-прокси: проверь влияние выбранной настройки на них, не меняя их контракты. Не смешивай эту задачу с общим рефакторингом endpoints.

## Приёмка

- Реальная upstream-передача multipart дольше 100 секунд завершается успешно в Web и Torrent при исправном Files.
- Отмена браузера останавливает upstream Web-запрос и чтение потока; отмена Torrent также работает.
- Зависшая передача завершается согласно явно выбранной политике; ресурсы освобождаются.
- Обычная загрузка, ошибки Files и привязка импортированного файла сохраняют прежние контракты.

## Доказательства этой проверки

Внешний probe повторил точные регистрации из текущего исходника: Web/Torrent `TimeoutSeconds=100`. Незавершающийся HTTP handler получил отмену по этому timeout примерно через 100 секунд. Без переданного токена отмена имитированного browser request не завершила `PostAsync` и не отменила upstream. Это проверка поведения `HttpClient`, а не полноценный прогон через работающие Web/Files; реальная долгая multipart-передача остаётся обязательной проверкой исправления.
