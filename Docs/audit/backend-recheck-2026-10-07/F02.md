# F02 — отзыв старого refresh после сброса пароля

Срез: `d6563a2`, повторная проверка 2026-10-07. **Статус: закрыт. Прежний приоритет: P1. Исправлять повторно не нужно.** Исправление вошло после исходного отчёта, коммит `568e42b`.

## Что было сломано

Другой запрос мог прочитать refresh устройства до reset, а подписать access JWT после commit сброса. При отзыве остальных устройств только по времени новый `iat` оказывался позже `RevokedAt`. Такой JWT проходил даже после загрузки отзыва в cache и сохранял доступ прежней сессии после восстановления аккаунта.

## Почему сейчас закрыто

- [CreateTokenCommandHandler.cs:19](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Identity/Features/CreateToken/CreateTokenCommandHandler.cs:19) по-прежнему может прочитать refresh до reset, но [строка 36](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Identity/Features/CreateToken/CreateTokenCommandHandler.cs:36) передаёт в JWT `RefreshToken.Id` как session ID.
- [RefreshTokensStorage.cs:81](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Identity/Persistence/Services/RefreshTokensStorage.cs:81) удаляет прежние refresh всех устройств; [строки сохранения отзыва](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Identity/Persistence/Services/RefreshTokensStorage.cs:103) задают каждому устройству `MaxSessionId = max(Id)` удаляемых refresh.
- [TokenRevocationCache.cs:42](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.GrpcServer/XAuth/TokenRevocationCache.cs:42) отклоняет `sid <= MaxSessionId` и токены без sid. Время подписи такого JWT уже не определяет результат.
- [ConfirmResetPasswordCommandHandler.cs:202](/Users/liis/Projects/BarkCloud/Backend/BarkCloud.Identity/Features/ConfirmResetPassword/ConfirmResetPasswordCommandHandler.cs:202) сохраняет расходование reset, смену пароля, удаление refresh, отзывы и новую пару в одной транзакции.

## Динамическая проверка

Существующий [ResetPassword_StaleRefreshReadBeforeReset_IssuedAccessIsRevoked](/Users/liis/Projects/BarkCloud/Tests/Backend/BarkCloud.Identity.IntegrationTests/ResetPasswordTests.cs:165) прошёл на отдельном PostgreSQL 18 с реальными миграциями, хендлерами и feed:

1. Настоящий `CreateToken` устройства `other` читает старый refresh и останавливается до выпуска JWT.
2. Настоящий reset удаляет старый refresh, записывает порог sid и создаёт новую пару текущего устройства.
3. Тест ждёт следующую секунду и продолжает подпись: `iat` старого JWT уже позже reset.
4. Настоящий `DbRevocationFeed` загружается в cache. JWT старого refresh отклоняется; JWT новой пары принимается.

[Соседняя проверка](/Users/liis/Projects/BarkCloud/Tests/Backend/BarkCloud.Identity.IntegrationTests/ResetPasswordTests.cs:133) подтверждает отзыв старых access обоих устройств и работоспособность новой пары. Покрыты также отказ создания refresh, отмена commit, конкурентные подтверждения и `RevokeOtherSessions=false`.

## Scope и критерии закрытия

Production-правки по прежнему F02 не требуются. Сохранить регрессионный тест и убрать пункт из списка открытых дефектов. Проверенные критерии: старые refresh удалены; старый JWT отвергается даже при подписи после reset; новая пара не отзывается, включая выпуск в ту же секунду; rollback не расходует reset и сохраняет прежние сессии.

Не заменять sid обратно временным порогом и не добавлять блокировки refresh/reset без новой подтверждённой задачи. Изложенный interleaving уже обработан существующим исправлением.

## Ограничение доказательства

Это динамический regression реального reset/refresh на PostgreSQL, а не полный сетевой прогон сервисов за nginx. Тест проверяет отклонение **после загрузки feed**. Межсервисная синхронизация отзывов асинхронна: обычно следующий polling; поздние commit покрывает полная сверка. Не выдавать это за мгновенный отказ всех реплик в момент reset. Документированный крайний случай refresh-запроса, зависшего дольше срока хранения отзыва, этим тестом не проверен.
