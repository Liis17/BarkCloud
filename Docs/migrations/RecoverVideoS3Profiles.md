# Восстановление доступа к видео после ручного переключения S3

Случай 2026-10-04: копирование выполнено в `https://s3.fra.databucket.eu / cloud-video`, обычное сохранение создало `videos-v2`, прежний бакет R2 удалён. Существующие файлы сохраняют `StorageProfileId = videos-v1`, поэтому Files получает `The specified bucket does not exist` от старого подключения. Перезапуск не меняет эту привязку.

Использовать [RecoverVideoS3Profiles.sql](RecoverVideoS3Profiles.sql) для этого конкретного случая. Скрипт переносит параметры подключения из `videos-v2` на все профили прежнего физического R2-бакета, включая старые версии и legacy. ID, версии, роли, активность, квоты и привязки файлов сохраняются; `videos-v2` и посторонние профили не меняются. Credentials читаются из БД и не выводятся. Предыдущее и новое подключения записываются в обычный журнал ревизий.

1. В обычных настройках выбрать `videos-v2` и выполнить «Проверить доступ». Убедиться, что копирование завершено и необходимые объекты находятся в новом бакете.
2. Выполнить SQL целиком **в БД `configuration`**, с остановкой при ошибке. При стандартных именах контейнеров Builder и наличии файла на сервере:

   ```sh
   docker exec -i cloud-postgres sh -c 'PGPASSWORD="$POSTGRES_PASSWORD" exec psql -X -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d configuration' < Docs/migrations/RecoverVideoS3Profiles.sql
   ```

3. Дождаться завершения текущих загрузок/обработки и перезапустить Files через «Обслуживание» (либо `docker restart cloud-files`). Files загружает подключения при старте.
4. Открыть видео заново, чтобы получить свежую временную ссылку. При запросе `Range: bytes=0-0` доступная копия должна вернуть HTTP 206.

Скрипт исправляет маршрутизацию к существующим копиям. После удаления источника финальная досинхронизация и повторная сверка с его содержимым невозможны. Объекты, которые не успели скопироваться, из этого скрипта не восстанавливаются. Обычное «Применить миграцию» требует доступного источника; его защита также отклоняет назначение, уже связанное с другим профилем.

SQL проверяет ожидаемые ID и адреса, полноту credentials и режим R2. Все изменения и ревизии выполняются одной транзакцией с блокировкой профилей. Повторный запуск не создаёт повторных ревизий. При отличающихся настройках скрипт прекращает работу без изменения данных.

Проверено на изолированном PostgreSQL 17: переключение связанных обычных и legacy-профилей (включая HTTP/порт R2), сохранение ID/версий/ролей/флагов/квот/привязок файлов, неизменность назначения и постороннего профиля, корректные снимки ревизий, повторный запуск; полный откат при отсутствующем/неожиданном назначении, неправильном R2-режиме, пустом secret, неожиданном источнике и ошибке записи ревизии. Скрипт на production-сервере агентом не выполнялся.
